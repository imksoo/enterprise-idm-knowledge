1. プロトコル全体マップ

エンタープライズ ID 管理では、複数のプロトコルが異なる役割を担う。認証（AuthN）・認可（AuthZ）・プロビジョニングの3層を正しく理解し、シーンに応じて適切なプロトコルを選択することが設計品質の要である。本資料では SAML 2.0、OpenID Connect (OIDC)、OAuth 2.0、SCIM 2.0 を横断的に比較・解説する。

プロトコル3層モデル

🔒 認証（AuthN）層 — 「あなたは誰か？」を確認する

SAML 2.0 AuthN XML

Security Assertion Markup Language。2002年策定のエンタープライズSSO業界標準。XMLベースのアサーションでIdP（認証基盤）からSP（サービス提供者）へユーザー属性を安全に伝達する。

登場年: 2002年（SAML 2.0は2005年）

主な採用シーン: 社内・SaaS SSO、官公庁・金融機関のオンプレミス連携

主要製品: Active Directory Federation Services (ADFS)、Shibboleth、Entra ID、Okta

OpenID Connect (OIDC) AuthN JWT

OAuth 2.0 を基盤とした認証レイヤー。2014年策定。JWT（JSON Web Token）形式のIDトークンでユーザー情報を伝達。モバイルアプリ・SPA・マイクロサービスに最適。

登場年: 2014年（OpenID Foundation策定）

主な採用シーン: モバイルアプリ認証、B2C サービス、クラウドネイティブ環境

主要製品: Entra ID (Azure AD)、Auth0、Keycloak、Google Identity

🔓 認可（AuthZ）層 — 「何をしてよいか？」を制御する

OAuth 2.0 AuthZ REST

認可の委譲フレームワーク。2012年RFC策定。アクセストークンを用いて、リソースオーナーの代理でクライアントにAPIアクセス権限を委譲する。OIDC の基盤プロトコル。

登場年: 2012年（RFC 6749）

主な採用シーン: Web API認可、サードパーティアプリ連携、マイクロサービス間認証

主要製品: Azure AD B2C、Auth0、Okta、Kong

XACML AuthZ

eXtensible Access Control Markup Language。OASIS策定の細粒度アクセス制御ポリシー記述言語。Policy Decision Point (PDP) / Policy Enforcement Point (PEP) モデルで動的認可を実現。

大規模な医療・金融システムでの採用実績あり。SailPoint、Axiomatics などが対応。日本での採用は限定的。

👥 プロビジョニング層 — 「アカウントを自動管理する」

SCIM 2.0 プロビジョニング JSON/REST

System for Cross-domain Identity Management。2015年RFC策定。JSON/RESTベースの標準プロビジョニングAPI。HR系システム→IDM→SaaSの自動連携を実現する。

登場年: 2015年（RFC 7643/7644）

主な採用シーン: 入退社時の自動アカウント作成・削除、SaaS一括プロビジョニング

主要製品: Entra ID (Provisioning)、Okta、SailPoint、Saviynt

LDAP / AD ディレクトリ

Lightweight Directory Access Protocol。1993年策定のディレクトリサービスアクセス標準。Active Directory の根幹プロトコル。オンプレミス環境では現在も主要なID管理手段。

LDAPv3（RFC 4511）。389ポート（非暗号化）、636ポート（LDAPS）。日本のオンプレ環境での残存率が高く、移行時の互換性考慮が必要。

🔐 SAML 2.0 詳解

Security Assertion Markup Language 2.0 | OASIS 標準 | 2005年策定

SAML 2.0 は、XMLベースのデータフォーマットとプロトコルを用いて、異なるセキュリティドメイン間（IdP から SP）でユーザーの認証・属性情報を安全に交換するための業界標準である。エンタープライズ SSO の礎として、金融・公官庁・製造業を中心に広く採用されている。

SP-initiated SSO フロー

最も一般的な SAML SSO フロー。ユーザーが SP のリソースにアクセスすることを起点とする。

SAML 2.0 の強み・弱み

✅ 強み❌ 弱み・課題
エンタープライズ環境での採用実績が豊富。ほぼ全ての商用 IdP/SP が対応XML の冗長性により、トークンサイズが大きくなりやすい（数 KB 〜 数十 KB）
XML 署名・XML 暗号化による強固なセキュリティモデルモバイルアプリ・SPA との相性が悪い（ブラウザリダイレクト前提）
属性マッピングによる詳細なユーザー情報伝達（グループ・役職・部署等）XML パーサーの実装複雑性。XML Signature Wrapping (XSW) 攻撃に注意が必要
Single Logout (SLO) の標準化。SP 側からのログアウト伝播が可能SP メタデータ（XML）の管理・更新が煩雑。証明書更新時のダウンタイムリスク
IdP-initiated SSO により、ポータルからのアプリ起動が容易IdP-initiated SSO は CSRF 攻撃への対策が別途必要
日本国内の SIer・ベンダーの知識・サポート体制が充実最新のゼロトラストアーキテクチャとの統合が複雑になる場合がある

SAML メタデータの主要要素

IdP メタデータ（提供側）

  • EntityID: IdP の一意識別子（URL形式推奨）
  • SSO Service URL: 認証リクエスト受付 URL
  • SLO Service URL: ログアウトリクエスト受付 URL
  • X.509 Certificate: 署名検証用証明書
  • NameID Format: 対応する識別子形式一覧

SP メタデータ（消費側）

  • EntityID: SP の一意識別子
  • ACS URL: Assertion Consumer Service URL（SAMLレスポンス受付）
  • SLO Service URL: ログアウト応答受付 URL
  • X.509 Certificate: 暗号化アサーション受信用証明書
  • Required Attributes: SP が必要とする属性一覧

🔑 OpenID Connect / OAuth 2.0 詳解

OpenID Connect 1.0 (2014) | OAuth 2.0 RFC 6749 (2012) | JWT / JSON ベース

OAuth 2.0 は認可の委譲フレームワークであり、OpenID Connect (OIDC) はその上に認証レイヤーを追加したプロトコルである。SAML に比べて軽量（JSON/JWT）で、モバイルアプリ・SPA・マイクロサービスへの適合性が高い。現在、多くのクラウドサービスの主要認証プロトコルとして採用されている。

認可コードフロー（Authorization Code Flow）

OIDC/OAuth 2.0 で最もセキュアかつ推奨されるフロー。サーバーサイドアプリおよびモバイルアプリ（PKCE併用）で使用する。

クライアント

認可サーバー

PKCE（Proof Key for Code Exchange）の重要性: モバイルアプリや SPA では client_secret を安全に保持できないため、PKCE（RFC 7636）を使用する。認可コード横取り攻撃を防ぐ。現在はすべての認可コードフローで PKCE 使用を推奨（RFC 9700）。

トークン種別と用途

トークン種別形式用途有効期限主要クレーム
ID TokenJWT（署名付き）ユーザーの認証情報。「誰が認証したか」を証明。クライアントアプリが消費する短命（数分〜1時間程度）sub, iss, aud, exp, iat
Access TokenJWT または OpaqueAPIアクセスの権限証明。Bearer トークンとして Authorization ヘッダーに付与短命（1時間程度）scp, roles, oid, exp
Refresh TokenOpaque（通常）アクセストークンの更新。ユーザー再認証なしでトークンを取得する長命（数日〜数ヶ月）。回転式が推奨不透明（クライアントは内容を読まない）

SAML 2.0 vs OpenID Connect 使い分けガイド

シーン推奨プロトコル理由
レガシーな社内 Web アプリ SSOSAML 2.0既存システムの対応実績が豊富。SP メタデータ交換による設定が確立されている
新規 SaaS 連携（Salesforce・ServiceNow 等）OIDC または SAML 2.0両方対応していることが多い。新規なら OIDC を優先
モバイルアプリ（iOS / Android）認証OIDC + PKCESAML はブラウザリダイレクト前提で Native App に不向き
SPA（React / Vue）認証OIDC (Auth Code + PKCE)Implicit Flow は非推奨（RFC 9700）。PKCE付き認可コードフローが推奨
Web API の認可制御OAuth 2.0スコープ（scope）による細粒度制御。Bearer トークンによる stateless な API 保護
マイクロサービス間認証OAuth 2.0 Client Credentialsユーザー不在のサービス間認証。client_id + 証明書で M2M を実現
政府・金融の厳格なシステムSAML 2.0 + FIDO2SAML の成熟した監査・コンプライアンス対応。FIDO2でフィッシング耐性を追加

OAuth 2.0 グラントタイプ一覧

認可コードフロー（推奨）

サーバーサイドアプリ・モバイルアプリ（PKCE併用）向け。最もセキュアで汎用的なフロー。認可コードをバックチャネルでトークンと交換する。

response_type=code

クライアント・クレデンシャルフロー

ユーザー不在のサービス間（M2M）通信向け。バックグラウンドジョブ・デーモン・マイクロサービス間API呼び出しに使用。

grant_type=client_credentials

デバイスコードフロー

ブラウザを持たないデバイス（IoT・CLI ツール等）向け。デバイスコードを別端末で入力して認証する。

grant_type=device_code

リフレッシュトークンフロー

期限切れのアクセストークンをユーザー再認証なしで更新するフロー。セッション継続に使用。リフレッシュトークンのローテーションを推奨。

grant_type=refresh_token

👥 SCIM 2.0 詳解

System for Cross-domain Identity Management 2.0 | RFC 7643 / RFC 7644 | 2015年策定

SCIM 2.0 は、異なるシステム間でのユーザー・グループ情報の自動同期を標準化した REST API 仕様である。入社・異動・退社のライフサイクルイベントに連動して、複数の SaaS やディレクトリサービスへのアカウント管理を自動化することで、人的ミスの削減と即時性の向上を実現する。

自動化による主要効果: SCIM 対応 SaaS への一括プロビジョニングにより、入社翌日（または当日）からすべてのシステムを使用可能な状態にできる。退職処理でも即時の全システムアカウント無効化が実現し、内部不正リスクを大幅に低減する。

日本特有の考慮事項

🏭 日本企業のプロトコル採用傾向

オンプレミス残存企業（製造・金融・公官庁）: SAML 2.0 が主流。ADFS を IdP として活用し、社内ポータル・SaaS 連携の基盤とするケースが多い。

クラウドネイティブ企業・スタートアップ: OIDC + OAuth 2.0 を採用。Entra ID（Azure AD）または Auth0 を IdP とした構成が増加。

移行期にある中堅・大企業: SAML/OIDC の併用。Entra ID が両プロトコルに対応することで段階的な移行を実現。

🏫 業界別の傾向

金融・銀行: SAML 2.0 + スマートカード（ICカード）認証の組み合わせが多い。FIDO2 への移行も進みつつある。

公官庁・自治体: LGWAN 環境との分離に注意。マイナンバーカードを使ったフェデレーション認証（SAML ベース）が普及しつつある。

製造業: SAP 連携（SAML/OIDC）と工場系システム（LDAP/Kerberos）の混在が一般的。Entra Connect による段階的移行が主流。

IGA 連携と SCIM の標準化動向（2026年時点）

日本国内でも IGA（Identity Governance and Administration）製品の導入が加速しており、HR システム → IGA → SaaS の自動プロビジョニング基盤として SCIM 2.0 の採用が標準化しつつある。

🔢 HR システムの SCIM 対応

SmartHR・カオナビ等の国産 HR SaaS が SCIM 送信元として機能するようになり、Entra ID / Okta への直接連携が可能になった。

✅ セキュリティ規制の強化

退職者アカウントの即時無効化義務（情報漏洩対策）が企業に求められるようになり、手動管理から SCIM 自動化への移行が加速している。

📈 ゼロトラスト移行との連動

ゼロトラストアーキテクチャでは「最小権限の原則」が重要。SCIM + IGA による属性ベースのアクセス制御（ABAC）が実装基盤となっている。

移行プロジェクトの典型的な落とし穴: SAML から OIDC への切り替え時に、Single Logout (SLO) の挙動が変わることを見落とすケースが多い。OIDC は SLO が標準化されておらず、Front-Channel Logout / Back-Channel Logout の仕様を個別に実装する必要がある。事前の動作検証が必須。
