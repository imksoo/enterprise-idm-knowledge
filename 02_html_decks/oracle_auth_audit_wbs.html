Oracle Database 認証・監査近代化

実装プロジェクト WBSガイド — NSSOL SE・プロジェクトマネージャー向け

📋 プロジェクト概要・全体像

このドキュメントはOracle Database環境における認証方式の近代化・監査基盤の整備・特権アクセス管理の強化を実際に推進するための実装ガイドです。 J-SOX・FISCの証跡要件を満たしながら、段階的に「共有SYSDBA撲滅→個人単位追跡確立→機微データ監査」を実現するWBS粒度の手順を記載します。

🎯 プロジェクト目標

  • 共有SYSDBA/SYSTEM運用の撲滅
  • 個人単位の操作追跡確立
  • 機微データへのFGA適用
  • J-SOX・FISC証跡要件の充足
  • 外部委託先アクセスの統制

👥 プロジェクト体制（最小構成）

  • PM（情報システム部門）
  • Oracle DBA（設計・実装）
  • AD管理者（Kerberos連携）
  • セキュリティ担当（監査設計）
  • PAM製品エンジニア
  • 内部監査・コンプライアンス（受入）

🔭 スコープ定義と前提整理

スコープIN（本プロジェクトで扱う）

  • Oracle Database 12c〜23ai/26ai（オンプレミス・Azure VM・OCI）
  • 管理者アカウント（SYSDBA/DBAロール保有者）
  • アプリケーション接続ユーザー（APスキーマ）
  • バッチ・ETL連携ユーザー
  • Active Directory Kerberos連携
  • Unified Auditing・FGA設計
  • PAM製品連携（CyberArk / Delinea）
  • 外部委託先（SIer・運用ベンダー）アクセス統制

スコープOUT（別プロジェクトで扱う）

  • アプリケーションロジックの改修
  • Oracle以外のDB（SQL Server・PostgreSQL）
  • TDE（透過的データ暗号化）の詳細設計
  • Oracle GoldenGate・Data Guard構成変更
  • OSレベルのID管理（RHEL SSSD等）
  • ネットワーク設計（DMZ・ファイアウォール）
⚠️ 日本企業でよくある前提認識の齟齬： 「監査要件を満たす = ログを取得する」という理解で進めると失敗しやすい。 J-SOX・FISCが求めるのは「誰が・何を・いつ・なぜ操作したか」の個人単位追跡であり、 共有SYSDBA運用のまま監査ログを増やしても「誰がやったか不明」なログが積まれるだけで要件を満たさない。 認証整備（個人ID化）と監査整備は必ずセットで進める。

Phase 0 で使用するSQL例

-- 1. 全ユーザーとデフォルトプロファイル確認
SELECT username, account_status, profile, authentication_type,
     last_login, created
FROM dba_users
ORDER BY account_status, username;

-- 2. SYSDBAホルダー全確認
SELECT * FROM v$pwfile_users;

-- 3. 直近90日間ログインなし（休眠）ユーザー
SELECT username, last_login, account_status
FROM dba_users
WHERE last_login < SYSDATE - 90
   AND account_status = 'OPEN';

-- 4. システム権限を直接付与されているユーザー（ロール経由でない）
SELECT grantee, privilege, admin_option
FROM dba_sys_privs
WHERE grantee NOT IN (SELECT role FROM dba_roles)
ORDER BY grantee;

-- 5. 現行password verifier確認（10g verifierが残っていないか）
SELECT username, password_versions
FROM dba_users
WHERE password_versions LIKE '%10G%';

-- 6. 現行監査ポリシー確認
SELECT policy_name, enabled_opt, entity_name
FROM audit_unified_enabled_policies;

sqlnet.ora 設定例（Kerberos有効化）

# $ORACLE_HOME/network/admin/sqlnet.ora

# Kerberos認証を有効化（NONE は完全無効化）
SQLNET.AUTHENTICATION_SERVICES = (BEQ, KERBEROS5)

# Kerberos設定ファイルの場所
SQLNET.KERBEROS5_CONF = /etc/krb5.conf

# サービスのkeytab
SQLNET.KERBEROS5_KEYTAB = /etc/oracle/oracle.keytab

# 許容するKDCとのスキュー（秒）
SQLNET.KERBEROS5_CLOCKSKEW = 300

# ベーシック認証のフォールバック禁止（重要：強制Kerberos化）
SQLNET.FALLBACK_AUTHENTICATION = FALSE

DBユーザー作成例（Kerberos外部認証）

-- ADユーザー tanaka@EXAMPLE.LOCAL に対応するDBユーザー作成
CREATE USER "TANAKA@EXAMPLE.LOCAL"
IDENTIFIED EXTERNALLY AS 'KERBEROS5:tanaka@EXAMPLE.LOCAL';

-- 最小限の権限のみ付与（CREATE SESSION + 業務ロール）
GRANT CREATE SESSION TO "TANAKA@EXAMPLE.LOCAL";
GRANT DBA_OPERATIONS_ROLE TO "TANAKA@EXAMPLE.LOCAL";

-- 接続テスト（Kerberosチケット取得後）
-- $ kinit tanaka@EXAMPLE.LOCAL
-- $ sqlplus /@db_service_name

Unified Auditing ポリシー実装例

-- 1. ログオン監査ポリシー
CREATE AUDIT POLICY pol_logon
ACTIONS LOGON, LOGOFF;
AUDIT POLICY pol_logon;

-- 2. DDL変更監査（全ユーザー対象）
CREATE AUDIT POLICY pol_ddl
ACTIONS CREATE TABLE, DROP TABLE, ALTER TABLE,
CREATE USER, DROP USER, ALTER USER,
GRANT, REVOKE;
AUDIT POLICY pol_ddl;

-- 3. 特権ユーザー（SYS・DBA）の全操作監査
CREATE AUDIT POLICY pol_privileged
PRIVILEGES ALL PRIVILEGES
WHEN 'SYS_CONTEXT(USERENV,ISDBA ) = TRUE'
EVALUATE PER SESSION;
AUDIT POLICY pol_privileged;

-- 4. 監査ログ確認
SELECT event_timestamp, dbusername, action_name,
object_schema, object_name, unified_audit_policies
FROM unified_audit_trail
WHERE event_timestamp > SYSDATE - 1
ORDER BY event_timestamp DESC;

FGA実装例（個人情報テーブルの列単位監査）

-- 顧客テーブルの機微列（氏名・電話・マイナンバー）アクセス監査
BEGIN
DBMS_FGA.ADD_POLICY(
object_schema => 'APP_SCHEMA',
object_name => 'CUSTOMER_MASTER',
policy_name => 'FGA_CUSTOMER_PII',
audit_column => 'CUSTOMER_NAME,PHONE_NUMBER,MY_NUMBER',
enable => TRUE,
statement_types => 'SELECT,UPDATE',
-- 監査条件：業務時間外（20時〜7時）のアクセスを監査
audit_condition => 'TO_NUMBER(TO_CHAR(SYSDATE,''HH24'')) NOT BETWEEN 7 AND 20',
handler_schema => 'AUDIT_SCHEMA',
handler_module => 'AUDIT_ALERT.NOTIFY_SECURITY_TEAM'
);
END;
/

-- FGA監査ログ確認（Unified Audit Trailとの統合）
SELECT event_timestamp, dbusername, object_schema,
object_name, sql_text
FROM unified_audit_trail
WHERE fga_policy_name = 'FGA_CUSTOMER_PII'
ORDER BY event_timestamp DESC;

🏰 Phase 3: 特権管理強化（Database Vault / PAM本格化）

目標: 特権ユーザーによる業務データ不正アクセスの技術的禁止・JIT化 ／ 期間目安: 12〜24週間

⚠️ 主要リスクと対策

🔴 移行後に自動化ジョブが停止する
原因: バッチ・ETLが旧認証方式（固定パスワードや10G verifier）に依存している
対策: Phase 0でジョブ×認証依存を完全棚卸し。移行前に非本番環境で全ジョブ検証を実施。
🔴 Kerberos障害がDB接続全断になる
原因: DNS・時刻同期・keytab有効期限のいずれかが崩れると接続不可
対策: フォールバック手順（Break Glass ID）を事前整備。KDC冗長化・keytab更新アラート設定。
🟡 Database Vault有効化後に運用スクリプトが失敗する
原因: DBAが全テーブルにアクセスできることを前提にした運用スクリプトが多い
対策: Simulation Mode（最低2〜4週間）で違反を洗い出してから本番適用。
🟡 FGAログが大量発生して運用できない
原因: 監査条件を絞り込まず全件監査にした場合
対策: 業務担当・コンプライアンスと「何を監査するか」を合意してから実装。業務上の大量取得はホワイトリスト化。
🟡 委託先SIerがPAM経由を嫌がり旧接続を要求する
原因: 運用手順変更・接続速度・不便さへの抵抗
対策: 契約・SLAレベルでPAM経由を義務付け。移行前に委託先への十分な説明と訓練を実施。
🟢 監査ポリシー過剰でDBパフォーマンスが低下する
原因: 全SQL・全ユーザーへの広範な監査適用
対策: 監査はログオン・DDL・特権操作・FGA対象列に絞る。負荷テストをDEV/STGで実施。
