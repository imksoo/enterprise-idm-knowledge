🏢 前提: 典型的な日本企業のID環境

日本企業の多くは、Active Directory を中心としたオンプレミス基盤に業務システム・ファイルサーバー・Windows PC が依存する構成からスタートする。 この現状を正確に把握した上で移行パターンを選択することが、プロジェクト成功の第一条件である。

  • SIer保守契約に紐づく共有ID
  • ベンダー依存で設計情報が不在
  • 帳票・印刷サーバーのKerberos依存
  • 年2回の大規模リリース慣行

📌 4パターン選択の軸

  • DCクローズ期限の有無
  • Kerberos依存アプリ数
  • 既存AD構成の健全性
  • 社内SE能力とベンダー依存度
  • 予算規模(単年 vs 複数年)
  • M&A/グループ統合の有無
パターン1: Lift and Shift

📦 DCクローズ急ぎ・AD構成変更不可・短期実現向け

所要期間: 6〜12ヶ月 ／ コスト感: 中〜高 ／ ADオンプレ継続: ◎
既存の Active Directory 構成を大きく変えずに Azure VM 上へ移送、または Entra Domain Services を補完利用する延命策。 データセンター更改期限対応に有効だが、Active Directory 設計の問題をそのまま持ち込むため将来の整理計画が必要。

Phase 1 DCクローン評価・AD健全性確認 (1〜2ヶ月)
孤立OU・未使用アカウント・過剰権限グループを棚卸し。Kerberos SPN・サービスアカウント一覧を作成。 Azure VM スペック設計（DS3v2以上推奨）。ExpressRoute / VPN 帯域要件確認。
Phase 2 Azure VM DC 構築・サイト構成設計 (2〜4ヶ月)
Azure VM 上にセカンダリ DC を展開。ADサイトリンク設定（認証トラフィック制御）。 フェイルオーバーテスト実施。既存ファイルサーバーのAzure Files移行判断。
Phase 3 Entra Connect 導入・PHS有効化 (1〜3ヶ月)
Entra Connect によるディレクトリ同期開始。Password Hash Synchronization 有効化でクラウド認証の足場を整備。 パイロット部門でのMFA展開。SaaS認証のEntra ID経由化（優先度の高いアプリから）。

評価

✅ 向いている企業

  • DCを置く物理サーバーがなくなる（DCクローズ期限あり）
  • AD構成変更の承認が取れない
  • Kerberos依存アプリが多く、短期での改修が不可能
  • とにかく早く「動く状態」を維持したい
  • 予算は確保できているが人員が少ない

❌ 向いていない企業

  • AD設計が老朽化しており、抜本改修が必要
  • 長期的にゼロトラスト・ADフリーを目指している
  • コスト最小化が最優先（Azure VM AD の維持費は高い）
  • M&AやグループID統合が近い将来に控えている

💰 コスト感

Azure VM DC (DS3v2 × 2台 冗長構成)

月額 ¥80,000〜¥150,000（VMコスト）

+ ExpressRoute/VPN費用 + 運用費。Entra Domain Services は別途 ¥30,000〜/月。

パターン2: Hybrid Coexistence

🔄 日本企業主流 — 段階移行・既存資産活用・リスク分散

所要期間: 12〜24ヶ月 ／ コスト感: 中 ／ ADオンプレ継続: ◎ → △
Active Directory と Entra ID を長期間並行運用しながら、ユーザー・端末・アプリを段階的に移行する。 日本企業で最も現実的な主流パターン。Entra Connect によるディレクトリ同期が基盤となる。

Phase 1 同期基盤構築 — Entra Connect + PHS (2〜4ヶ月)
Entra Connect インストール・UPN サフィックス統一（@domain.com形式）。Password Hash Synchronization 有効化。 Entra Hybrid Join パイロット展開（IT部門端末50台）。Entra Connect Health 監視設定。
Phase 2 クラウド認証強化 — Conditional Access + MFA全社展開 (3〜6ヶ月)
Microsoft Authenticator 全社展開（段階ロールアウト）。Conditional Access ポリシー設計（レガシー認証ブロック）。 SaaS アプリの SAML/OIDC 移行（ADFS依存からEntra ID経由へ）。Named Location 設定（海外ブロック等）。
Phase 3 特権管理近代化 — LAPS + JIT権限 (3〜5ヶ月)
Windows LAPS 展開（端末ローカル管理者パスワード個別管理）。Entra ID PIM（Privileged Identity Management）でAD管理者のJIT昇格。 サービスアカウントの gMSA 化推進。特権アカウント棚卸しと不要権限削除。
Phase 4 ADフリー化推進 — Entra Join + GPO代替 (4〜9ヶ月)
新規端末を Entra Join で展開（ドメイン参加不要）。Intune でポリシー・証明書・アプリ配布を代替。 残存 Kerberos 依存アプリの改修またはアプリプロキシ経由化。AD依存範囲の継続的縮小。

評価と注意点

✅ 向いている企業

  • 既存AD資産が比較的健全
  • 段階的リスク分散を優先
  • Microsoft 365 展開済み
  • Kerberos依存が一部ある
  • 3〜5年での完全移行を計画

⚠️ 日本固有の注意点

  • UPN不一致問題（社内IDと異なる）
  • Entra Connect 設定ミスで同期エラー多発
  • SIer担当者がEntra Connect未経験
  • GPO移行漏れで端末設定が抜ける
  • MFA登録率が低い部署への対応

💰 コスト感

  • Entra ID P2ライセンス必要（CA・PIM）
  • Intune: Microsoft 365 E3以上に含む
  • 初期構築コスト: ¥300〜¥800万
  • 運用費: 月額 ¥30〜¥80万
  • ユーザー教育コスト別途
パターン3: Cloud Native

☁️ 新規事業 / スタートアップ / 全社クラウド移行済み

所要期間: 3〜6ヶ月（新規） ／ コスト感: 低〜中 ／ ADオンプレ継続: ✕
Active Directory を持ち込まず、Entra ID を中心に端末・認証・運用を設計するパターン。 新設組織・スタートアップ・既存AD廃止済み企業が対象。レガシー業務アプリへの対応が最大の課題となる。

⚠️ よくある失敗パターンと対策

日本企業で繰り返される典型的な移行失敗と、その対策。

🔧 技術的な失敗パターン

Entra Connect 設定ミス（UPN不一致）
最多発 — 同期開始後にユーザーがログインできない

原因: オンプレADの UPN サフィックスが @company.local のまま。Entra ID のカスタムドメインと一致しない。
対策: Entra Connect 設定前に全ユーザーの UPN を @company.com（検証済みドメイン）に変更。パイロット100件で確認後に全展開。

GPO移行漏れによる設定抜け
Intune移行時に多発

原因: GPO一覧を把握せずにIntune展開。セキュリティ設定・証明書配布・スクリプト実行が抜け落ちる。
対策: Microsoft MMAT（Migration Tool for GPO）で移行可否を事前チェック。GPO→Intune マッピング表を作成。

Conditional Access のレガシー認証ブロック漏れ
セキュリティ強化の抜け穴

原因: IMAP/POP3/Basic認証がブロックされず、MFAをバイパスする経路が残存。
対策: Azure AD Sign-In logs でレガシー認証の利用状況を確認後、段階的にブロック（まずReport-onlyモードで影響確認）。

Entra Hybrid Join 端末の登録失敗
大規模展開時に20〜30%が登録失敗することも

原因: SCP（Service Connection Point）設定不備、DNS名前解決失敗、GPO遅延適用。
対策: dsregcmd /status で登録状態確認。SCP確認 (Get-ADObject -Identity "CN=62a0ff2e-...")。フォレスト内全DCで SCP 複製確認。

🏢 組織・プロセスの失敗パターン

SIer責任分界の曖昧化による意思決定遅延
日本企業で最も多い停滞原因

症状: 設計判断が発生するたびにベンダーへのエスカレーションが必要で、月単位で遅延。
対策: RACI表を移行開始前に確定。情報システム部門が「設計オーナー」として意思決定権を明示的に持つ。SIerは「実装パートナー」に留める。

利用者教育の後回し → MFA登録率低迷
展開3ヶ月後もMFA登録率50%以下が続く

症状: IT部門が技術整備を優先し、エンドユーザー向け説明を後回しにした結果、展開が止まる。
対策: 展開6週間前から段階的なコミュニケーション開始。ヘルプデスクスクリプト・QRコード付き手順書・部門別チャンピオン制度の活用。

フォールバック（退避経路）未設計
同期停止・誤ポリシーで業務停止

症状: 移行完了後も SIer の共有 ID が無効化されず、認証ログに異常なアクセスが混入。
対策: 外部委託アカウントを一覧化し、Privileged Identity Management + 期限付き権限で管理。保守契約終了時の自動無効化フローを設計。
