脅威の全体像と分類

ID攻撃は3つのフェーズで構成される。それぞれに対して異なる防御層が必要。

🔑

① 資格情報窃取

パスワード・ハッシュ・チケットを盗み出す初期フェーズ。フィッシング、マルウェア、LSASS ダンプが主手法。

🔀

② 横展開・昇格

窃取した資格情報を使い、端末から端末へ、一般ユーザーから管理者へと権限を拡大するフェーズ。

🏴

③ 持続性確保

Golden Ticket、バックドアアカウント、スケジュールタスクなどで長期間の潜伏と再侵入経路を確保するフェーズ。

なぜIDが攻撃の標的になるか

技術的・組織的な理由から、IDは現代攻撃の「必ず通る経路」になっている。

🔍 ID中心攻撃が増加する6つの理由

🔓 IDは万能鍵
正規の資格情報を使った攻撃は、マルウェアの署名検知を回避できる。「正規ユーザー」として振る舞うため、従来のセキュリティ機器が検知しにくい。
🏢 AD集中管理の弱点
日本企業の多くは単一ADフォレストで全社を管理。Tier0（ADそのもの）への到達 = 全社完全掌握。KRBTGT1アカウントの侵害で「万能チケット」が生成できる。
📧 フィッシング成功率の高さ
標的型フィッシングの成功率は15〜30%（IPA報告）。クリック1回でローカル管理者権限を取得し、そこから横展開が始まる。
⏰ ライフサイクル管理の欠如
退職者・異動者のIDが長期間有効のまま残存。日本企業では手動管理が多く、棚卸し実施率は低い（IPAセキュリティ白書2024）。
🔁 パスワード再利用
ローカル管理者パスワードを全端末で共有する慣行が残存。1台の侵害が即座に全端末横展開につながるPass-the-Hash攻撃の温床。
☁ クラウド移行後の盲点
Entra IDとオンプレADの同期環境では、オンプレ側の侵害がクラウドIDへ伝播するリスク。Entra Connect サーバーがTier0扱いになる。

Mimikatz等のツールでメモリからNTLMハッシュまたはKerberosチケットを直接抽出。 パスワードそのものは不要で、ハッシュをそのまま認証に使用（Pass-the-Hash）、 またはチケットを注入して別端末へアクセス（Pass-the-Ticket）する。 Windows標準のプロトコルを悪用するため、ネットワークIDS単独では検知困難。

⚠ 被害範囲
  • 管理者権限奪取により社内端末・サーバーへの横展開（ラテラルムーブメント）
  • ドメインコントローラー到達後、DCSync攻撃で全ユーザーのハッシュ一括窃取
  • 全社規模のランサムウェア展開の踏み台
  • 検知されるまで平均「数週間〜数ヶ月」潜伏可能（Verizon DBIR 2024）
✅ 推奨防御策

🛡 多層防御 — 4つの制御レイヤー

  • Credential Guard の有効化 Windows 11 / Server 2025 で標準有効。VBS（仮想化ベースセキュリティ）でLSASSを隔離し、メモリからのハッシュ抽出を根本的に困難にする。GPOで一括適用可能。
  • LSA Protection の有効化 LSASS を Protected Process Light (PPL) として動作させ、管理者権限でも直接メモリアクセスを制限。レジストリ設定 + Secure Boot との組み合わせで効果最大化。
  • Protected Users セキュリティグループへの追加 高権限アカウントを Protected Users に追加すると、NTLMv1/v2・RC4暗号化・資格情報キャッシュが無効化。Kerberos AES 強制。DAなど全Tier0アカウントに適用推奨。
  • NTLM の段階的無効化 NTLM Auditing → NTLM Block（ドメイン内）の順で段階移行。レガシーシステムの依存状況を事前確認し、Kerberos移行計画と並走。Server 2025では既定でNTLM v1無効。

Credential Guard + LSA Protection は設定変更のみで適用可能。Defender for Identity は2週間で展開可能。

AD に認証できる権限があれば誰でも実行可能。SPNが設定されたサービスアカウントの Kerberosサービスチケット（TGS-REP）はサービスアカウントの秘密鍵で暗号化されており、 オフラインでのパスワード解読が可能。脆弱なパスワードなら数時間以内に解読される。 Hashcat/Johnなど汎用ツールで実行可能で、攻撃者の敷居が低い。

⚠ 被害範囲
  • サービスアカウントのパスワード解読 → SQLサーバー・IIS・バッチ処理の完全制御
  • サービスアカウントが過剰権限（DomainAdmins等）の場合、即座にドメイン掌握
  • 攻撃はADログに正規のKerberos要求として記録され、検知が困難
  • レガシーシステムの「変えられないパスワード」が長期的な弱点になる
✅ 推奨防御策

🛡 サービスアカウント刷新計画

  • サービスアカウントのパスワード複雑化（25文字以上） RC4暗号化TGSチケットを解読するには長いランダムパスワードが効果的。ただし根本解決にはならないため、gMSA移行と並走させる。
  • Managed Service Account / gMSA への移行 gMSA（グループ管理サービスアカウント）は120文字ランダムパスワードを自動ローテーション。SQLサーバー、IISアプリプール、スケジュールタスクに対応。Kerberoastingの根本排除。
  • AES暗号化強制（RC4無効化） msDS-SupportedEncryptionTypes で AES256 のみ許可。RC4 は解読が容易なため、レガシー互換性を確認しつつ段階無効化。
  • Entra ID PIM によるサービスプリンシパル管理 クラウド側のサービスアカウント（アプリ登録）は PIM でロール割り当てを時間制限化。シークレットはAzure Key Vaultで管理。
  • Defender for Identity による異常なTGS要求検知 短時間に多数のSPNへのTGS要求を検知してアラート。初期検知として有効だが、低速攻撃には限界があるため根本対策と組み合わせる。

🟠 3ヶ月以内
サービスアカウント棚卸し → gMSA移行計画 → Defender for Identity 導入の順で実施。

Golden Ticket は KDC（KRBTGT アカウント）のハッシュを使用して、 任意のユーザー・グループ・SIDに偽造したTGTを作成する攻撃。 パスワードを変更してもハッシュが同じであれば有効。 Silver Ticket はサービスアカウントのハッシュでTGSを偽造し、KDCを経由しないため KDC側の検知が困難という特性がある。いずれもドメイン完全制圧後の「権力確保」に使われる。

⚠ 被害範囲
  • ドメイン内全サービスへの完全アクセス（最大10年有効のチケット偽造が可能）
  • パスワードリセット後も攻撃者が有効なチケットを保持し続ける
  • Silver Ticket はKDCを経由しないためネットワーク監視での検知が困難
  • KRBTGT侵害 = ドメインの「信頼の根拠」が失われた状態（フォレスト再構築が必要な場合も）
✅ 推奨防御策

🛡 KRBTGT保護とTier0管理

  • KRBTGT パスワードの計画的ローテーション（2回連続） KRBTGTは前回のハッシュも保持するため、1回だけでは不完全。12〜24時間空けて2回連続でローテーションが必要。Microsoft公式スクリプトを使用。年1回以上実施推奨。
  • AD Tiering (Tier 0/1/2 分離) の実装 DCへの管理アクセスをTier0管理者・PAWからのみに制限。Tier1サーバー管理者がDCへ直接ログインできない設計。認証ポリシーサイロ（Windows Server 2012R2+）で強制可能。
  • Microsoft Defender for Identity による異常チケット検知 Golden Ticket の検知シグネチャを保有。チケットの有効期間異常、SID履歴異常、KDC非経由認証などを機械学習で検知。Sentinel と連携して自動対応も可能。
  • DC へのアクセスを PAW (Privileged Access Workstation) に限定 DC管理は専用のPAWからのみ許可。PAWはインターネット・メール接続不可、一般業務と完全分離。物理またはVM（専用HW）で構成。
  • ADバックアップとオフライン保管 侵害後のフォレスト再構築に備えたシステムステートバックアップ。バックアップ管理者アカウントを本番ADから分離（Backup Admin Tier）。テープ/オフラインストレージへの定期エクスポート。
🏢 日本企業の実情

KRBTGTのパスワードが「AD構築時から一度もローテーションされていない」ケースが多数。 構築後5〜10年経過したAD環境では、KRBTGTハッシュが侵害されれば即座に全社制圧が可能な状態。 特権管理製品（CyberArk等）と組み合わせ、DC管理操作のセッション録画を推奨。

KRBTGTローテーションは計画メンテナンス窓口で即実施可能。Defender for Identity は最優先で展開。

被害拡大の速度はラテラルムーブメント速度で決まる（ランサムウェア対策の要諦）。 初期侵害から全社展開まで24〜72時間というケースが多い。 LAPSが導入されていない環境では、ローカル管理者パスワードが全端末共通であるため、 1台の侵害が即座に全端末への横展開につながる。最終的にGPOまたはPsExecで 全社一斉にランサムウェアを実行する。ADバックアップ/バックアップサーバーも 同一ドメインに参加している場合、バックアップごと暗号化される。

SMB署名が無効の環境ではNTLMリレー攻撃も組み合わせて使用。管理共有（C$, ADMIN$）が 有効なまま放置された環境では横展開の難易度が極めて低い。

⚠ 被害範囲
  • 全社端末・サーバーの暗号化（バックアップサーバーを含む場合も）
  • 業務完全停止（製造業では生産ライン停止、病院では診療停止）
  • 身代金要求（数千万円〜数十億円）+ データ流出による二次被害
  • AD再建に数週間〜数ヶ月を要するケースも（実例：ALPHV/Blackcat被害企業）
✅ 推奨防御策

🛡 ランサムウェア横展開対策 — 5層防御

  • Windows LAPS の即時展開（端末ごとに異なるローカル管理者パスワード） Windows 11 22H2 / Server 2019+ で標準提供。GPOで一括展開可能。端末ごとに120文字ランダムパスワードを自動ローテーション。ADまたはEntra IDに安全保管。横展開を単一端末内に封じ込める最重要対策。導入コスト：¥0（OS標準）。
  • SMB 署名の強制（Require SMB Signing） GPOで SMBServer/SMBClient の RequireSecuritySignature を有効化。NTLMリレー攻撃を根本的に遮断。Windows Server 2025では既定有効。レガシー機器との互換確認が必要。
  • 管理共有（C$, ADMIN$）の無効化または制限 汎用ユーザーからの管理共有アクセスをファイアウォール（Windows Defender Firewall）でブロック。管理系サブネット以外からのアクセスを禁止。ランサムウェアの横展開経路を大幅に削減。
  • マイクロセグメンテーション（管理セグメント分離） 端末セグメント↔サーバーセグメント↔管理セグメント↔バックアップセグメントを独立したVLAN/ファイアウォールポリシーで分離。管理ポート（RDP 3389, WMI, SMB 445）は管理セグメントからのみ許可。
  • ADバックアップとオフライン/イミュータブル保管 Windowsシステムステートバックアップを毎日取得。バックアップサーバーは本番ADに非参加（別ドメインまたはワークグループ）。AWS S3 Object Lock / Azure Immutable Blob等でランサムウェア耐性を確保。
🏢 日本企業への教訓（2023〜2024年被害事例より）

国内製造業A社：端末1台の侵害から72時間でAD掌握、全工場停止。LAPSとSMB署名が 未導入だったことが被害拡大の主因。復旧に3週間・数億円を要した。 医療機関B院：バックアップサーバーが同一ADに参加していたため、ランサムウェア暗号化を回避できず。 電子カルテ停止で手書き診療を2週間継続。

Evilginx、Modlishka等のAiTM（Adversary-in-the-Middle）ツールで、 正規のログイン画面をリアルタイムでプロキシし、ユーザーの入力とMFA認証後の セッションCookieを同時窃取する。MFAを突破しているため、 「MFAさえあれば安全」という誤解を突く。2022年のLapsus$グループや 2023年のMGMリゾーツ侵害でも使用された現在進行形の主流攻撃手法。

⚠ 被害範囲
  • Microsoft 365 / Teams / SharePoint への完全アクセス（メール全文・社内ファイル閲覧）
  • セッションCookieは有効期限まで（数時間〜数日）MFA再認証不要で使用可能
  • BEC（ビジネスメール詐欺）の起点：取引先への振込先変更メール等
  • 内部から社外へのデータ流出（正規ユーザーとして振る舞うため検知困難）
✅ 推奨防御策

🛡 フィッシング耐性MFAへの移行

  • Number Matching MFA の有効化（即時可能） Authenticatorアプリでプッシュ承認時に画面に表示された2桁数字の入力を要求。プッシュ乱射による誤承認を防止。Microsoft Entra管理センターで認証ポリシー変更のみで有効化。コスト：¥0。
  • FIDO2 / Windows Hello for Business への移行（フィッシング耐性MFA） 秘密鍵がデバイスから出ないため、AiTMプロキシでの資格情報窃取が原理的に不可能。YubiKey（物理キー）またはWindows Hello（生体認証）。Entra ID への対応は完了済み。
  • Conditional Access: 準拠済みデバイスのみ許可 Intune管理下の準拠済みデバイスからのアクセスのみ許可するポリシー。窃取したCookieを別デバイスで使用しようとすると条件付きアクセスでブロック。Entra ID P1以上で設定可能。
  • Token Protection の有効化（Entra ID P2） アクセストークンをデバイスに紐付け（Proof-of-Possession）。別デバイスへのトークン転送を無効化し、セッションハイジャックを根本的に防止。2024年GA済み。
  • Entra ID Protection + 条件付きアクセスによるリスクベース認証 異常なサインイン場所・IP・デバイスを機械学習で検知し、自動的に再認証・MFA強化・アカウントブロックを適用。セッション窃取後のアクセスも高リスク判定で遮断。
📰 実例：Lapsus$グループの手口（2022年）

Microsoft、Nvidia、Samsung、Okta等に侵入。MFAプッシュ通知を深夜に乱射し 眠れなくなったユーザーが誤承認するまで送り続ける手法（MFA Bombing）を多用。 Okta社の顧客サポートシステム侵害では、下請け業者のアカウントが突破口となった。

日本企業では人事システムとADの連携が自動化されておらず、 退職処理をITチームへ手動連絡する運用が多い。連絡漏れ・優先度後回しで 長期間有効なままになるケースが頻発。委託先SEが自社のID管理ルールを知らず、 必要以上の権限で長期アクセスするケースも多い。 IPA「組織内部不正による情報漏洩実態調査（2024年）」では、 内部不正の32%が「退職後のID悪用」によるものと報告。

⚠ 被害範囲
  • 顧客情報・製品設計図・営業秘密の競合他社への流出
  • 個人情報保護法違反による行政指導・課徴金・レピュテーション損害
  • 委託先SEによる過剰なシステム変更・データ削除・バックドア設置
  • 内部調査に多大なコストと時間（平均3〜6ヶ月の調査期間）
✅ 推奨防御策

🛡 IDライフサイクル自動化とIGA導入

  • HR連携による自動無効化（JML: Joiner-Mover-Leaver） 人事システム（SAP HR / WorkDay / 独自DB）とAD/Entra IDを連携し、退職日当日の自動無効化・翌日削除を実装。Entra ID Lifecycle Workflows（P2）またはMIM/FIM活用。「連絡もれ」を構造的に排除。
  • IGA製品による定期アクセスレビュー（Access Certification） SailPoint IdentityNow / Saviynt等で、管理者・業務マネージャーが半期に1回「このユーザーにこの権限は必要か」を承認/却下するプロセスを自動化。不要権限の蓄積（Permission Creep）を防止。
  • PAMによる委託先のセッション録画と接続制御 CyberArk / BeyondTrust で委託先のRDP/SSHセッションを録画・テキスト化。承認ワークフロー経由でのみ接続許可。作業終了後に即時アクセス無効化（JIT Access）。監査証跡として6ヶ月保管。
  • Active Directory の無効アカウント定期棚卸し PowerShell / AD管理ツールで「90日間未使用アカウント」を定期抽出し、業務部門との突合→無効化。SecureCube Access Check（国産IGA）も日本語UIで棚卸し支援機能を提供。
  • Just Enough Administration (JEA) で委託先の操作範囲を限定 PowerShell JEAロールで委託先SEが実行できるコマンドレット・引数を厳密に制限。「サーバーA のIISのみ再起動可能」等の細粒度委任が可能。転写ログ（Transcription）で操作内容を完全記録。
🏢 日本の実情（IPA報告・現場事例より）

大手製造業での調査では、棚卸し実施前のADアカウントのうち15〜20%が 「退職者・異動者」の孤立アカウント（Orphaned Account）だったケースも。 特に「兼務者」「出向者」「再雇用者」のIDは複数システムに点在し、 手動管理での全件捕捉が困難。IGA導入による自動棚卸しが根本解決。
