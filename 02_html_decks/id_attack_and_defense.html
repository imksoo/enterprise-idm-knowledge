👑 Active Directoryが攻撃者にとって「王冠」である理由

Active Directoryはオンプレミス環境のあらゆる認証・認可の基盤。1つのDomain Adminアカウントを支配すれば、全Windowsサーバー・PC・ファイル共有・Exchange・Webアプリ・さらにEntra Connect経由でMicrosoft 365まで支配できる。攻撃者がADを攻略すれば「鍵のマスターキー」を手にしたに等しい。

🏗️ ADの支配範囲（オンプレ）

  • 全ドメイン参加Windowsサーバー
  • 全ドメイン参加クライアントPC
  • ファイルサーバー（CIFS/SMB）
  • SQL Server（Windows認証）
  • IIS / Webアプリ（統合認証）
  • 仮想化基盤（vCenter AD連携）
  • バックアップシステム
  • NAS・ストレージ

☁️ ADの支配範囲（ハイブリッド）

  • Entra Connect経由でM365全体
  • Exchange Online / Teams
  • SharePoint Online / OneDrive
  • Azure リソース（RBAC連携）
  • SSO連携のSaaS全般
  • ADFS連携アプリ
  • Entra Hybrid Join端末

⚠️ 日本企業固有のリスク要因

  • 1人のAD管理者が全権限を保持
  • SIer常駐者にDomain Admins付与
  • NTLM認証が無効化されていない
  • サービスアカウントPW10年超変更なし
  • 退職者アカウントが残留
  • MFAが管理者にも未適用
  • バックアップが同一AD管理者で管理

A

Pass-the-Hash / Pass-the-Ticket 攻撃

NTLM悪用 Kerberos悪用 横展開 危険度: 最高
パスワードそのものを知らなくても、メモリから窃取したNTLMハッシュ（Pass-the-Hash）やKerberosチケット（Pass-the-Ticket）を再利用してリモートシステムに認証できる。Mimikatz / Impacket / Cobalt Strikeで容易に実行可能。防御側はパスワードを変えても対処不可能であり、ハッシュ/チケット自体の無効化が必要。

🔴 攻撃手順（ステップ）

  1. フィッシングまたはExploit経由で1台のWindowsマシンに初期アクセスを確立
  2. ローカル管理者権限を取得（UAC Bypass、権限昇格脆弱性）
  3. mimikatz sekurlsa::logonpasswords でlsass.exeメモリをダンプ
  4. NTLMハッシュ（RC4 / NTLM形式）を抽出。パスワード不要
  5. mimikatz sekurlsa::pth でハッシュを使ったシェルを起動（PtH）
  6. 他サーバーへのSMB/RDP接続で認証成功（同一PWハッシュが使い回されている場合は全台に展開）
  7. Kerberos TGTが抽出できた場合はmimikatz kerberos::pttでPtT（Pass-the-Ticket）を実行
  8. Domain Adminsのハッシュ取得後、全ADドメインを掌握
💥 影響範囲
共有ローカル管理者パスワードを使っている環境では全端末が対象。Domain Adminsのハッシュが取られれば全ドメイン参加サーバー・PCが対象に。侵害から全社への横展開は数時間以内に完了する。

🛡️ 技術的対策（具体的な設定・製品）

  • Windows LAPS 全台展開：端末ごとに異なるローカル管理者PWを自動ローテーション。GPO「LAPS/PasswordSettings」から設定。AD属性またはEntra IDに保管。
  • Credential Guard 有効化：GPO「Windows Defender Credential Guard」→「Virtualization Based Security」を有効化。VBSでlsassメモリを保護しNTLMハッシュの抽出を阻止。
  • LSA Protection（RunAsPPL）：レジストリ「HKLM\SYSTEM\CurrentControlSet\Control\Lsa\RunAsPPL=1」設定。lsassを保護プロセスとして動作させMimikatzを無効化。
  • Protected Users グループ：高権限ユーザーをProtected Usersに追加。NTLM認証・DES/RC4・資格情報キャッシュを自動禁止。
  • NTLM段階的制限：GPO「Network Security: Restrict NTLM」で監査→ドメインアカウント制限→全面制限の順で移行。
  • SMB署名強制：GPO「Microsoft network server: Digitally sign communications (always)」を有効化。セッション改ざん・なりすましを防止。

B

Kerberoasting / Golden Ticket 攻撃

Kerberos悪用 サービスアカウント krbtgt 危険度: 最高
Kerberoastingはドメインユーザー権限のみで実行可能。SPNが登録されたサービスアカウントのチケットをDCにリクエストし、RC4で暗号化されたチケットをオフラインでクラックする。Golden Ticketはkrbtgtの秘密情報を用いて偽のKerberos TGTを作成する。一度取得すれば最大10年間有効で検知が困難。

🔴 攻撃手順（Kerberoasting）

  1. 一般ドメインユーザー権限を何らかの手段で取得（侵害PCへのアクセス等）
  2. setspn -Q */* または PowerShell / Impacket でSPN付きアカウントを列挙
  3. 各SPNアカウントのKerberosサービスチケット（TGS）をDCにリクエスト
  4. チケットはRC4-HMAC暗号化でローカル保存可能
  5. Hashcat / John the Ripper でオフライン辞書攻撃・ルールベース攻撃
  6. 解読したサービスアカウントPWで当該アカウントにアクセス
  7. Domain Admins権限を持つサービスアカウントなら全社掌握

🔴 Golden Ticket 攻撃手順

  1. DCSync権限（Replicating Directory Changes権限）を持つアカウントを確保
  2. mimikatz lsadump::dcsync /user:krbtgt でkrbtgtのNTLMハッシュを取得
  3. mimikatz kerberos::golden で任意ユーザーのゴールデンチケットを偽造
  4. 偽チケットをメモリにインジェクトしAD上の任意リソースにアクセス
  5. 最大10年間有効。パスワード変更後も（krbtgtを除き）有効なことが多い
💥 影響範囲
Kerberoasting：サービスアカウントが管理者権限を持つ場合は全社規模。Golden Ticket：全ADドメイン・全サービスが攻撃対象。krbtgtの二重リセットまで効果が持続する。

🛡️ 技術的対策

  • gMSA（グループ管理サービスアカウント）全面移行：120文字ランダムPWを自動ローテーション。RC4暗号化を使わないためKerberoasting不可能に。Active Directoryの標準機能（無償）。
  • AES暗号化強制：GPO「Network security: Configure encryption types allowed for Kerberos」でRC4/DESを除外。AES128/AES256のみ許可。
  • サービスアカウントの最小権限化：Domain Admins/Enterprise Adminsからサービスアカウントを除外。必要な最小権限のみに制限。
  • krbtgtパスワード定期二重リセット：6ヶ月〜1年ごとに2回連続でリセット。既存Golden Ticketを無効化。ADの設計として重要。
  • DCSync権限の監査と最小化：「Replicating Directory Changes All」権限を持つアカウントを定期棚卸し。
  • Defender for Identity：Kerberoasting・DCSync・Golden Ticketの異常なKerberosチケットリクエストをリアルタイム検知。

ランサムウェア（AD管理者乗っ取り→全社暗号化）

AD掌握 GPO悪用 全社暗号化 危険度: 壊滅的
現代のランサムウェアグループ（LockBit、Black Basta等）は侵入後すぐに暗号化しない。数日〜数週間かけてADを掌握してから実行することで復旧を困難にする「Big Game Hunting」が主流。バックアップを事前に破壊した後に実行するため、復旧には数週間〜数ヶ月を要する。

🔴 攻撃手順（ステップ）

  1. フィッシングメール・VPN脆弱性・公開サーバーの脆弱性で初期侵入
  2. C2（コマンド＆コントロール）サーバーとのビーコン通信を確立
  3. 数日かけてネットワーク内を静かに偵察。ADの構造・バックアップシステムを把握
  4. Kerberoasting/PtHでドメイン管理者権限を取得
  5. 全ドメイン参加端末に対してGPOまたはPsExecでランサムウェアを配布
  6. EDRの除外設定を追加し、ウイルス対策を無効化
  7. VSSコピーを削除（wmic shadowcopy delete）、バックアップエージェントを停止
  8. 週末・深夜・連休に合わせてXデーを設定し一斉暗号化を実行
💥 影響範囲
全ドメイン参加端末（数百〜数万台）が対象。バックアップが同一AD管理者で管理されていた場合、復旧手段も同時に失う。業務停止期間は平均2〜4週間、完全復旧まで数ヶ月に及ぶ事例もある。身代金要求は数千万円〜数億円。

🛡️ 技術的対策

  • Tiered Admin Model：Tier 0（DC管理）/ Tier 1（サーバー管理）/ Tier 2（PC管理）に管理者権限を分離。1アカウントでの全権限奪取を不可能に。
  • LAPS（ローカル管理者PW個別管理）：全端末で横展開を阻止。共通ローカル管理者PWによる一気展開を防ぐ。
  • バックアップID完全分離：バックアップシステムの管理者アカウントを本番ADと別フォレストまたはEntra IDのみで管理。本番AD侵害時でも復旧手段を温存。
  • Immutable Backup（不変バックアップ）：WORM・Retention Lock・オフラインコピーを組み合わせ。ランサムウェアによる削除・暗号化が不可能な状態を維持。
  • マイクロセグメンテーション：SMB/RDP/WinRMの端末間通信を管理セグメントのみに制限。横展開経路を物理的に断つ。
  • EDR全台展開：暗号化挙動・VSS削除・C2通信をリアルタイム検知。被害発覚の早期化。
  • PAW（特権アクセスワークステーション）：管理者は専用端末からのみ管理作業。メール・Web閲覧を行う端末からDCへのアクセスを禁止。

フィッシング → MFA疲労 → セッションハイジャック

AiTM Phishing MFA Fatigue Token Theft 危険度: 高
Adversary-in-the-Middle（AiTM）フィッシングはMFAをバイパスしてセッショントークンを直接窃取する。従来の「パスワード窃取→MFA回避困難」という防御の常識を覆す手法。2023年以降、Microsoft 365・Google Workspace・Oktaを狙う攻撃で急増。MFA疲労（大量承認リクエスト送付）との組み合わせも多発。

🔴 攻撃手順（AiTMフィッシング）

  1. Evilginx2 / Modlishka などのAiTMプロキシサーバーを攻撃インフラに構築
  2. 正規のMicrosoft/Okta/Google等のログインページと見分けのつかないフィッシングURLを生成
  3. ターゲットにフィッシングメールを送付。URLクリックでAiTMプロキシ経由のログインを誘導
  4. ユーザーがMFA含めたログインを完了すると、セッションCookieをプロキシが取得
  5. 攻撃者はそのCookieを使ってMFAなしで正規サービスにアクセス
  6. Exchange/SharePoint/OneDriveでメール転送ルール設定・機密データ窃取
  7. そのアカウントを起点にさらなる内部フィッシング・BEC（ビジネスメール詐欺）を実行

🔴 MFA疲労攻撃手順

  1. フィッシング等でユーザーのID/PWを入手（MFAあり環境）
  2. ログイン試行を繰り返し、認証アプリに大量の承認リクエストを送付
  3. ユーザーが間違えて、または疲れて「承認」を押す
  4. 認証完了。完全アクセスを取得
💥 影響範囲
侵害されたユーザーのM365データ全体（メール・ファイル・Teams）。そのユーザーの権限で到達可能な内部システム。CFO・経営者アカウントが侵害された場合はBEC詐欺・不正送金リスク。

🛡️ 技術的対策

  • FIDO2/パスキー移行：フィッシングサイトではFIDO2キーが機能しない設計（origin binding）。最もMFA疲労・AiTMに耐性のある認証方式。まず特権ユーザーから段階展開。
  • 番号照合MFA（Number Matching）：Microsoft Authenticatorの番号照合を有効化。MFA疲労攻撃で押し間違えるリスクを低減。
  • 条件付きアクセス（準拠デバイスのみ）：Entra ID P1以上。Intune準拠デバイスのみM365アクセスを許可。管理外端末からのセッション盗取を無効化。
  • Entra ID Protection（リスクベースCA）：異常なサインイン（匿名IP・海外等）を自動検知しブロックまたは再認証を要求。
  • Continuous Access Evaluation（CAE）：条件変化時にアクセストークンをリアルタイム失効。盗んだトークンの有効時間を短縮。
  • UEBA（ユーザー行動分析）：通常と異なる時間帯・場所・操作量のアクセスを検知し、SOCにアラート。

サービスアカウント悪用（権限過剰・パスワード不変）

Kerberoasting 権限昇格 長寿命PW 危険度: 高
日本企業では「システム構築時に設定したサービスアカウントのパスワードを一度も変えていない」ケースが極めて多い。さらにDomain Admins権限を付与したまま放置されているケースも散見される。攻撃者にとって最も狙いやすい「長期間利用可能な特権への近道」である。

🔴 攻撃手順

  1. 一般ユーザー権限でドメインにアクセス（侵害PC経由）
  2. PowerShell Get-ADServiceAccount -Filter * でサービスアカウントと設定SPN一覧を取得
  3. Kerberoastingでサービスチケット（TGS）を一括取得
  4. Hashcatで辞書攻撃（8文字以下・単語+数字のPWは数時間でクラック）
  5. 解読したPWでサービスアカウントにログイン（対話型ログオン禁止設定がない場合）
  6. Domain Admins権限を持つサービスアカウントなら即座に全ドメイン掌握
  7. 解読したPWを他システムにもスプレー攻撃（パスワード使い回し）
💥 影響範囲
サービスアカウントが持つ権限範囲全体。Domain Admins権限を持つサービスアカウントが1件でも存在すれば、全社停止シナリオに直結する。同じPWが他システムで使い回されていれば被害が多段階に拡大する。

🛡️ 技術的対策

  • gMSA全面移行：AD標準機能（無償）。120文字ランダムPWをDCが自動生成・配布。Kerberoastingを実質的に無効化。SQL Server / IIS / Scheduled Tasksなど多くのサービスに対応。
  • PAMボールト（手動管理アカウント用）：gMSA非対応のサービスアカウントをCyberArk/Delineaで管理。90日以下でPW自動ローテーション。
  • 最小権限原則の徹底：Domain Admins/Enterprise Adminsからサービスアカウントを全削除。対象サーバーのローカルサービス権限のみに制限。
  • 対話型ログオン禁止：GPO「Deny log on locally」にサービスアカウントを追加。不正使用のリスクを削減。
  • SPN棚卸しと不要SPN削除：Kerberoastingの攻撃対象となるSPNを最小化。
  • サービスアカウント棚卸し：90日以上ログオン実績のないサービスアカウントを無効化。IGA導入で継続的な棚卸しを自動化。

内部不正・退職者残留アカウント

内部脅威 ライフサイクル管理 データ持ち出し 危険度: 高
退職・異動後もアカウントが有効なまま放置されるケースが多い。人事システムとIDシステムの連携が手動の場合、削除漏れは常態化する。悪意ある内部者は退職直前に大量データをダウンロードし、退職後もVPN経由でアクセスを続けることがある。平均検知まで197日という統計が示すように、長期間気づかれない。

🔴 攻撃シナリオ（内部不正）

  1. 退職を決意した従業員が退職日の1〜2ヶ月前から顧客リスト・設計書等を自宅PCにコピー開始
  2. クラウドストレージ（Google Drive・Dropbox等）への大量アップロード（DLPが未整備なら検知不可）
  3. 退職後もVPNアカウント・SaaSアカウントが有効なままならアクセス継続
  4. 競合他社への情報提供または転職時の持ち込み
  5. 情報漏洩が発覚するのは数ヶ月後（競合製品発売・訴訟等）

🔴 残留アカウント悪用シナリオ

  1. 退職者のADアカウントが無効化されず30日以上経過
  2. そのアカウント情報をダークウェブで購入した攻撃者がVPNログイン
  3. 内部ネットワーク上で正規ユーザーとして活動（検知困難）
  4. 機密データ取得・ランサムウェア展開の起点として利用
💥 影響範囲
そのユーザーが持っていた全アクセス権限範囲（AD + SaaS全般）。情報漏洩の損害賠償・競争上の損失・行政処分リスク。インテリジェンスが持ち出された場合は数年にわたる損失が生じることも。

🛡️ 技術的対策

  • IGA自動プロビジョニング：人事システムの退職日と連動して退職当日にアカウントを自動無効化。SailPoint / Entra ID Governance / Okta Lifecycle Managementで実装。
  • 全SaaSへのSSO統合：Entra IDをIdPとして全SaaSをSSO接続。AD/Entra IDのアカウント無効化で全SaaSへのアクセスが自動遮断される状態を作る。
  • アクセスレビュー（Certification）：四半期ごとに管理者がチームメンバーの権限を再確認。不要権限を定期除去。Entra ID GovernanceまたはIGAツールで実装。
  • UEBA（ユーザー行動分析）：退職予定者・異動者の大量ダウンロード・深夜アクセス・外部送信等の異常を検知。Microsoft Sentinel UEBAで実装。
  • JIT（Just-in-Time）権限：常時権限ではなく、業務申請ベースで必要な期間だけ権限を付与。Entra PIMまたはCyberArk JITで実装。
  • DLP（データ損失防止）：大量ダウンロード・外部メール添付・クラウドストレージ同期を検知・ブロック。Microsoft Purview DLPで実装。
