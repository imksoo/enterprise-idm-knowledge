📋 JMLとは何か — HR→IT連携の重要性

JML（Joiner / Mover / Leaver）とは、従業員のライフサイクル（入社・異動・退職）に伴うIDとアクセス権限の変化を自動管理する仕組みです。 人事システム（HRIS）をIDの「真実の源泉（Source of Truth）」として、AD・Entra ID・各SaaSへの自動プロビジョニング／デプロビジョニングを実現します。
⚠️ 日本企業で頻出する問題: 退職者のIDが無効化されないまま残存し、数ヶ月〜数年後に不正アクセスや情報漏洩につながる事例が後を絶ちません。 2023年の内部不正インシデントの約38%が「退職者・元委託先のID悪用」が関与していたとする調査報告があります（IPA「企業における情報セキュリティ実態調査2023」）。

なぜ手動管理では限界なのか

従業員が100人規模の組織でも、年間10〜20%の人員変動（入社・退職・異動）が発生します。1,000人規模になると年間100〜200件のID操作が必要になり、 IT担当者が手動でAD・Entra ID・Salesforce・kintone・Box・Slack・GitHubなど数十のシステムを個別に操作することは現実的ではありません。 また手動プロセスは「退職連絡がITに届くまでのタイムラグ」「担当者の繁忙期の対応遅延」「作業ミスによる権限残存」などのリスクを本質的に排除できません。

🔴 手動管理の典型的な問題

  • 人事→IT連絡フローが不定形（口頭・メール・Excelが混在）
  • 退職処理の担当者依存・引き継ぎ漏れ
  • SaaSアカウントの把握不完全（シャドーIT）
  • 異動時の旧権限削除忘れ（ゾンビ権限の蓄積）
  • 棚卸しが半年〜1年に1回程度で問題発見が遅延
  • J-SOX・ISMS監査での証跡提出が困難

🟢 JML自動化で実現すること

  • HRISの退職日フラグ → 当日自動無効化
  • 入社日前日にID・端末・アクセス権を準備完了
  • 異動申請承認 → 旧権限削除・新権限付与が同時実行
  • 全SaaS・オンプレシステムへの一括プロビジョニング
  • Certification（棚卸し）の自動スケジュールと通知
  • 全操作の監査ログが自動生成・SIEM連携可能

👤 Joiner（入社）プロセス

採用決定 → 入社当日のシステム準備完了 を自動化する

Joinerプロセスの目標は「入社初日から必要なシステムにアクセスできる状態」を、IT担当者の手動作業なしに実現することです。 内定承諾から入社日まで平均1〜3ヶ月あるため、この期間にHRISで登録された情報を元にID準備を進めることができます。

入社プロビジョニングのロール設計

所属部署・職種・役職の組み合わせで自動的に付与するロールを決定するのが「ロールモデル設計」です。 ABAC（属性ベースアクセス制御）を使い、department=営業部 AND grade=一般 のように条件を定義します。 入社時点で「最小権限」を付与し、必要に応じてリクエスト申請で追加付与する「Just-Enough-Access（JEA）」の原則が重要です。

🔄 Mover（異動・昇格）プロセス

部署異動・昇格・役職変更時の権限再評価を自動化する

Moverプロセスはしばしば最も実装が難しく、問題が見えにくい領域です。 入社・退職と異なり「アカウントを消す」のではなく「権限の一部を変更する」ため、変更漏れが積み重なっていきます。

⚠️ ゾンビ権限問題（Privilege Creep）

典型的なゾンビ権限の発生メカニズム:
Aさん（営業部→マーケ部→開発部と3年で3回異動）→ 各異動時に新権限は追加されたが旧権限は削除されず → 現在は営業・マーケ・開発の全システムにフルアクセス可能な「スーパーユーザー」に。 本人も「まだ使えるなら便利だからいいや」と申告しない → 監査で発覚。

Certification（棚卸し）との連携

異動イベントを検知した際に、新旧の権限が重複していないかを自動チェックする「イベント駆動型Certification」が有効です。 SailPoint IdentityNow や Saviynt では、異動発生時に自動でレビュータスクをマネージャーへ通知し、不要権限の承認削除を促します。 四半期ごとの定期棚卸しと組み合わせることで、ゾンビ権限をリアルタイムに抑制できます。

SOD（職務分離）違反の自動検知

Mover処理後にSOD（Segregation of Duties）ルールに違反していないかを自動チェックします。 たとえば「購買申請権限」と「購買承認権限」を同一人物が持つことは財務統制上の問題です。 IGA製品はSODルールをあらかじめ定義し、異動後の権限組み合わせを自動評価します。

🔗 HR連携パターン（国内HRISごとの実装方法）

JML自動化の成否はHRISとIGAの連携品質に大きく依存します。 海外製HRISはSCIM 2.0をサポートするものが増えていますが、国内製HRISは独自API・CSVエクスポートが主流です。

HRISシステムシェア・特徴連携方式注意点・実装ヒント
SAP SuccessFactors 外資系・大手日本企業に普及 SCIM 2.0 + SAP IAS連携、またはEntra直接コネクタ SuccessFactors Employee Central要。Entra ID Governanceとの標準コネクタあり
Workday 外資系・HR改革企業に普及 Workday→Entra ID プロビジョニング（標準対応） Workday Studio設定が必要。退職日フィールドのマッピングを慎重に設定すること

奉行シリーズ（OBC） 中小・中堅企業に普及 CSV定期エクスポート → SFTP → IGA取り込み リアルタイム連携困難。日次バッチが現実的。エクスポート列名のマッピング設計が必要

連携アーキテクチャの選択基準

🔵 SCIM 2.0直接連携

SAP SF / Workdayなど対応HRISと、Entra ID / Okta間の最もシンプルな構成。 設定はGUI上で完結し、リアルタイム同期が可能。大規模障害時のエラーハンドリング設計が重要。

🟡 中間IGA統合レイヤー

複数のHRISや複数のIDターゲットが混在する場合。SailPoint / One Identityが中間に入り、変換・ルーティングを担う。 コストと複雑度が上がるが、柔軟性は最も高い。

🟠 CSVバッチ連携

国内製HRISや古いシステムとの現実的な選択肢。日次バッチで差分を検出しプロビジョニング。 退職処理の遅延（最大1日）が発生するため、緊急退職手順を別途定めること。

  • KPI: Certification完了率・SOD違反件数

フェーズ間の依存関係と注意点

Phase 1のLeaver自動化は最も影響範囲が小さく（既存ユーザーのアカウントを消すだけ）、ビジネスリスクが低いため最初に着手すべきです。 Phase 2（入社自動化）はロールモデル設計が先行タスクとなり、設計の質が後々の運用コストに直結します。 Phase 3（Mover）は既存ユーザーの権限を変更するため最もリスクが高く、テスト期間を十分に確保してください。
