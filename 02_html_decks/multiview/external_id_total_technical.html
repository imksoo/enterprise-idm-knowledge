Windows LAPS と旧 Microsoft LAPS の違い

Windows LAPS は OS 標準機能として統合され、AD と Entra ID の両保存先、パスフレーズ、ポスト認証アクション、旧ポリシー互換性を備える。一方で旧 Microsoft LAPS は AD 中心の追加導入型であり、今から新規採用する優先度は低い。

LAPS の設計要点

共有ローカル管理者パスワードを残すと端末 1 台侵害から全域横展開につながる。LAPS では端末ごとに異なる秘密情報、短めのローテーション、閲覧権限の最小化、回収後の利用停止確認を組み合わせるべきである。

JEA の価値

フル管理者権限を配らず、特定業務に必要な PowerShell コマンドだけを許可できる。日本企業でよくある運用委託先への広い管理者権限付与を縮小するうえで有効である。

JEA 導入時の落とし穴

ロール設計が曖昧だと結局フル PowerShell を許可しやすい。許可コマンド、引数、外部実行、モジュール更新影響を明示し、トランスクリプションと SIEM 連携まで設計して初めて監査可能な最小権限になる。

Entra ID PIM の使いどころ

クラウド管理ロール、Privileged Access Group、Azure リソース管理の常時権限を避ける中核機能として用いる。MFA、承認、理由入力、時間制限、通知を標準化し、恒久的な active assignment を例外化するべきである。

JIT アクセスパターン

JIT は単に時間制限を付けるだけでは不十分である。チケット番号、対象システム、作業窓、承認者、操作ログ、作業後レビューを一連でつなぐと、内部不正と侵害後の権限悪用の両方を抑制できる。

PAW の実務的な位置づけ

PAW は上級管理者だけの専用端末ではなく、Tier 0 管理と一般業務を混在させないための基本制御である。メール添付や一般 Web 閲覧を行う端末から Tier 0 へ接続させないことが侵害耐性を大きく左右する。

Tier 0/1/2 分離の考え方

Tier 0 は認証基盤そのもの、Tier 1 はサーバー群、Tier 2 はクライアント管理であり、資格情報と管理端末を跨いで共有しないことが要点である。小規模組織でも論理分離は可能で、必ずしも人員を完全分離する必要はない。

踏み台サーバーの現代化

単なる RDP 中継では不十分で、接続元制限、多要素認証、セッション録画、SSH/RDP 双方の統合監査、ファイル転送制御が必要である。可能ならパスワード開示ではなくセッションプロキシ方式を採用する。

Linux sudo の適切な設計

Linux では `ALL=(ALL) ALL` の乱用が最も典型的な失敗である。`sudoers.d` に役割別ポリシーを分離し、コマンド許可を明示し、`NOPASSWD` を例外化し、I/O ログを中央送信する構成が望ましい。

特権監査ログ設計

監査ログは接続ログ、昇格ログ、コマンドログ、変更結果ログが別系統でも相関できるように `requester`、`target`、`session_id`、`ticket_id` を揃えるべきである。後から SIEM で結びつけられない設計は運用上の価値が低い。

サードパーティ PAM 製品の選定軸

CyberArk、BeyondTrust、Delinea はいずれも保管庫、セッション制御、昇格管理を持つが、強みは異なる。評価では Windows だけでなく Linux、ネットワーク機器、クラウドロール、API シークレット、運用委託先接続の扱いまで確認する必要がある。

サービスアカウント管理

人間の管理者よりも長寿命なサービスアカウントが侵害の温床になりやすい。保管庫によるローテーション、利用先棚卸し、Kerberos 連携やマネージド ID への移行計画を併せて進めるべきである。

Break Glass Account の扱い

緊急用アカウントは必要だが、通常の例外口として残すと統制が崩れる。除外対象は最小限にし、利用時は即時通知、事後レビュー、パスワード変更、保管方法の再確認を実施するべきである。
