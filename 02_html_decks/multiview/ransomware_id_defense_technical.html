横展開阻止の基本原則

ランサムウェア被害の深刻度は侵入そのものより横展開速度で決まる。SMB、RDP、WinRM、管理共有、共通管理者資格情報の同時対策が必要であり、単一制御だけでは止まりにくい。

SMB 署名の位置づけ

SMB 署名は万能ではないが、通信完全性の確保により古い中間者的手口やセッション改ざんの余地を狭める。ファイルサーバー、管理共有、レプリケーション経路を含めて段階的に強制する価値がある。

NTLM 無効化と制限

NTLM を一括停止するとレガシー業務が止まる場合があるため、監査から始めて依存先を洗い出し、管理者系アカウント、サーバー間通信、外部委託接続の順で縮退させるのが現実的である。

管理共有の扱い

管理共有 `C$` や `ADMIN$` は完全無効化が難しい環境もある。その場合でも接続元を踏み台や管理セグメントに限定し、一般端末からの到達性を断つことが重要である。

Credential Guard と LSA Protection

Credential Guard と LSA Protection はどちらも資格情報窃取耐性を高めるが、役割は異なる。前者は VBS による秘密情報分離、後者は `lsass.exe` の保護強化であり、併用することで防御層が厚くなる。

Protected Users の適用先

Protected Users は高権限者へ先行適用する価値が高いが、古いプロトコル依存を抱えるサービスアカウントには不向きである。ドメイン管理者、バックアップ管理者、認証基盤管理者から段階導入するのがよい。

DPAPI の実務上の注意

DPAPI 自体だけではなく、その前提となるユーザー資格情報やバックアップキー管理が重要である。侵害端末に保存されたブラウザ秘密情報やアプリ秘密情報の回収経路として見直す必要がある。

ネットワーク分離と検疫

検疫はインシデント時に初めて考えると失敗する。事前に管理系、バックアップ系、業務系の許可通信を整理し、EDR 連携でサーバー単位の遮断や限定通信モードへ切り替えられるようにしておくべきである。

バックアップの ID 分離

バックアップ製品の管理者を本番ドメイン管理者と兼務させると、1 つの資格情報侵害でバックアップ削除まで到達される。管理者、認証基盤、保管先、運用端末を分離しておくことが復旧性を左右する。

不変バックアップの意味

オフラインや WORM 保護のないバックアップは、侵害者にとって次の暗号化対象になりやすい。不変性、別認証系、復元演習の 3 点がそろって初めて実効的な復旧策になる。

Sentinel による AD 攻撃検知

Microsoft Sentinel では DC のセキュリティイベント、Sysmon、Defender 系シグナル、Entra ログを組み合わせることで DCSync、異常な認証失敗、管理者グループ変更、疑わしいチケット発行を相関できる。

Entra ID Protection の役割

オンプレミス侵害の文脈でも Entra ID Protection は重要である。侵害済み資格情報のクラウド側悪用や、ハイブリッド管理者の異常サインインを早期に把握し、条件付きアクセスと連動させられる。

日本企業でよくある全落ちパターン

単一の管理者アカウントがメール端末、運用端末、仮想基盤、バックアップ、AD 管理を兼務していると、フィッシング 1 回から全システム停止へ直結する。実被害ではこの資格情報集中が被害拡大の主要因になりやすい。

日本企業での対策優先順位

現実的な優先順位は、まず管理者分離、PAW、バックアップ ID 分離、Credential Guard、基本的なファイアウォール制御である。その次に NTLM 依存解消、マイクロセグメンテーション、Recovery Forest、分析自動化へ進む構成が実行しやすい。

Windows LAPS と旧 Microsoft LAPS の違い

Windows LAPS は OS 標準機能として統合され、AD と Entra ID の両保存先、パスフレーズ、ポスト認証アクション、旧ポリシー互換性を備える。一方で旧 Microsoft LAPS は AD 中心の追加導入型であり、今から新規採用する優先度は低い。

LAPS の設計要点

共有ローカル管理者パスワードを残すと端末 1 台侵害から全域横展開につながる。LAPS では端末ごとに異なる秘密情報、短めのローテーション、閲覧権限の最小化、回収後の利用停止確認を組み合わせるべきである。

JEA の価値

フル管理者権限を配らず、特定業務に必要な PowerShell コマンドだけを許可できる。日本企業でよくある運用委託先への広い管理者権限付与を縮小するうえで有効である。

JEA 導入時の落とし穴

ロール設計が曖昧だと結局フル PowerShell を許可しやすい。許可コマンド、引数、外部実行、モジュール更新影響を明示し、トランスクリプションと SIEM 連携まで設計して初めて監査可能な最小権限になる。

Entra ID PIM の使いどころ

クラウド管理ロール、Privileged Access Group、Azure リソース管理の常時権限を避ける中核機能として用いる。MFA、承認、理由入力、時間制限、通知を標準化し、恒久的な active assignment を例外化するべきである。

JIT アクセスパターン

JIT は単に時間制限を付けるだけでは不十分である。チケット番号、対象システム、作業窓、承認者、操作ログ、作業後レビューを一連でつなぐと、内部不正と侵害後の権限悪用の両方を抑制できる。

PAW の実務的な位置づけ

PAW は上級管理者だけの専用端末ではなく、Tier 0 管理と一般業務を混在させないための基本制御である。メール添付や一般 Web 閲覧を行う端末から Tier 0 へ接続させないことが侵害耐性を大きく左右する。

Tier 0/1/2 分離の考え方

Tier 0 は認証基盤そのもの、Tier 1 はサーバー群、Tier 2 はクライアント管理であり、資格情報と管理端末を跨いで共有しないことが要点である。小規模組織でも論理分離は可能で、必ずしも人員を完全分離する必要はない。

踏み台サーバーの現代化

単なる RDP 中継では不十分で、接続元制限、多要素認証、セッション録画、SSH/RDP 双方の統合監査、ファイル転送制御が必要である。可能ならパスワード開示ではなくセッションプロキシ方式を採用する。

Linux sudo の適切な設計

Linux では `ALL=(ALL) ALL` の乱用が最も典型的な失敗である。`sudoers.d` に役割別ポリシーを分離し、コマンド許可を明示し、`NOPASSWD` を例外化し、I/O ログを中央送信する構成が望ましい。

特権監査ログ設計

監査ログは接続ログ、昇格ログ、コマンドログ、変更結果ログが別系統でも相関できるように `requester`、`target`、`session_id`、`ticket_id` を揃えるべきである。後から SIEM で結びつけられない設計は運用上の価値が低い。

サードパーティ PAM 製品の選定軸

CyberArk、BeyondTrust、Delinea はいずれも保管庫、セッション制御、昇格管理を持つが、強みは異なる。評価では Windows だけでなく Linux、ネットワーク機器、クラウドロール、API シークレット、運用委託先接続の扱いまで確認する必要がある。

サービスアカウント管理

人間の管理者よりも長寿命なサービスアカウントが侵害の温床になりやすい。保管庫によるローテーション、利用先棚卸し、Kerberos 連携やマネージド ID への移行計画を併せて進めるべきである。

Break Glass Account の扱い

緊急用アカウントは必要だが、通常の例外口として残すと統制が崩れる。除外対象は最小限にし、利用時は即時通知、事後レビュー、パスワード変更、保管方法の再確認を実施するべきである。
