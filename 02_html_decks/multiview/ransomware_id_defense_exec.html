決断 2: Windows LAPS と旧 Microsoft LAPS の違い

Windows LAPS は OS 標準機能として統合され、AD と Entra ID の両保存先、パスフレーズ、ポスト認証アクション、旧ポリシー互換性を備える。一方で旧 Microsoft LAPS は AD 中心の追加導入型であり、今から新規採用する優先度は低い。

決断 3: Entra ID PIM の使いどころ

クラウド管理ロール、Privileged Access Group、Azure リソース管理の常時権限を避ける中核機能として用いる。MFA、承認、理由入力、時間制限、通知を標準化し、恒久的な active assignment を例外化するべきである。

横展開阻止の基本原則

ランサムウェア被害の深刻度は侵入そのものより横展開速度で決まる。SMB、RDP、WinRM、管理共有、共通管理者資格情報の同時対策が必要であり、単一制御だけでは止まりにくい。

SMB 署名の位置づけ

SMB 署名は万能ではないが、通信完全性の確保により古い中間者的手口やセッション改ざんの余地を狭める。ファイルサーバー、管理共有、レプリケーション経路を含めて段階的に強制する価値がある。

NTLM 無効化と制限

NTLM を一括停止するとレガシー業務が止まる場合があるため、監査から始めて依存先を洗い出し、管理者系アカウント、サーバー間通信、外部委託接続の順で縮退させるのが現実的である。

管理共有の扱い

管理共有 `C$` や `ADMIN$` は完全無効化が難しい環境もある。その場合でも接続元を踏み台や管理セグメントに限定し、一般端末からの到達性を断つことが重要である。

Credential Guard と LSA Protection

Credential Guard と LSA Protection はどちらも資格情報窃取耐性を高めるが、役割は異なる。前者は VBS による秘密情報分離、後者は `lsass.exe` の保護強化であり、併用することで防御層が厚くなる。

Protected Users の適用先

Protected Users は高権限者へ先行適用する価値が高いが、古いプロトコル依存を抱えるサービスアカウントには不向きである。ドメイン管理者、バックアップ管理者、認証基盤管理者から段階導入するのがよい。

DPAPI の実務上の注意

DPAPI 自体だけではなく、その前提となるユーザー資格情報やバックアップキー管理が重要である。侵害端末に保存されたブラウザ秘密情報やアプリ秘密情報の回収経路として見直す必要がある。

ネットワーク分離と検疫

検疫はインシデント時に初めて考えると失敗する。事前に管理系、バックアップ系、業務系の許可通信を整理し、EDR 連携でサーバー単位の遮断や限定通信モードへ切り替えられるようにしておくべきである。

❓ 経営層からよくある質問 Q&A
「なぜ今このタイミングで？」
Windows Server 2012/2016のサポート終了（2023〜2027年）と2029年問題が重なる「移行の最終機会」です。放置するほどリスクと移行コストが増大します。
「クラウドに移行すれば安全になるのか？」
クラウドは手段であり、ID管理の設計が不適切なら従来と同じリスクが残ります。重要なのは「誰が何にアクセスできるか」を正しく制御することです。
「既存ベンダーに任せればよいのでは？」
ID管理は全システムの「鍵管理」です。特定ベンダー依存は長期リスクになります。オープン標準ベースの設計で依存度を下げることが重要です。
「何から始めればよいか？」
まず「特権アカウントの棚卸し」と「退職者アカウントの確認」から着手できます。コストゼロで高リスクを即座に可視化できます。
「セキュリティ投資は費用対効果が見えにくいのでは？」
インシデント発生時のコスト（復旧・賠償・信頼毀損）と比較すれば定量化できます。保険料と同じ発想で、「発生確率×損失額」で評価することを推奨します。
