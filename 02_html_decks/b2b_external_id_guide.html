🌐 外部IDとは何か — 「外部ユーザー」の全類型

外部IDとは、自社の従業員ではないが、自社のシステム・データ・サービスにアクセスする必要がある人物やシステムのIDです。 B2B取引・委託業務・規制対応・M&Aなど様々な文脈で「外部ユーザー」が発生しますが、多くの企業では従業員IDと同じ管理体制が適用されていなかったり、まったく管理されていないケースが見られます。

外部ユーザーの6類型

🏢 取引先担当者

仕入先・販売先・物流会社の担当者。受発注システム・EDI・サプライヤーポータルへのアクセスが必要。担当者が変わるたびにID更新が必要。

🔧 SIer・保守ベンダー

システム構築・保守委託先の技術者。本番環境へのリモートアクセスが必要。プロジェクト終了後の即時無効化が最重要。特権アクセス管理（PAM）と連動すべき。

📋 監査法人・会計士

内部監査・外部監査・会計監査の担当者。財務データへの読み取りアクセス。監査期間中のみJITアクセスで付与し、終了後は即時削除。

🏛️ 規制当局・検査官

金融庁・監督官庁の検査担当者。コンプライアンス証跡の提出用アクセス。強固な本人確認（eKYC）と全操作ログが必須。

🤝 M&A相手先・JV

買収企業・合弁会社・業務提携先。統合プロジェクト期間中の限定アクセス。将来的に内部ユーザーへ移行するケースも多い。

🤖 システム間連携（API/EDI）

人ではなくシステムのID。EDIバイナリ接続・REST API・バッチファイル転送など。サービスアカウント・クライアント証明書・OAuth2クライアント資格情報フロー。

⚠️ 外部ID管理の3大問題

問題1: ゲストアカウント野放し（ゴーストID問題）

典型的シナリオ: A社との業務提携時にEntra B2Bでゲストアカウントを発行。2年後に提携終了。 しかし担当者の退職・引き継ぎ漏れでA社担当者のゲストアカウントが残存し続ける。 退職後もA社の元担当者がTeamsの共有ファイルにアクセス可能な状態が継続。 このようなゴーストIDはAzure ADテナントに数十〜数百件存在するケースが日本企業でも多数確認されている。

Microsoft Entraでは signInActivity を確認し、90日間サインインがないゲストアカウントを抽出することができます。 定期的な棚卸しと、招待元の責任者（スポンサー）によるレビュー承認ワークフローを整備することが対策の基本です。

問題2: EDI専用IDの長期放置

EDI（Electronic Data Interchange）システムとの接続に使われる専用ID・パスワード・証明書は、 一度設定すると「動いているから触らない」という方針のまま数年〜十数年更新されないケースがあります。 2024年の国内製造業のセキュリティ事故では、10年間更新されていないEDI接続パスワードが侵害され、 取引先の受注データが外部流出した事例が報告されています。

EDI接続パスワードの長期未更新
固定パスワードが辞書攻撃・ブルートフォースにさらされ続ける。EDIシステムのパスワード変更手順が文書化されていないため更新を避けがち。
AS2/SFTP接続の鍵管理不在
AS2証明書の有効期限切れが業務停止につながる事例多数。鍵・証明書の台帳管理と期限通知が必要。
複数取引先に同一鍵を使い回し
「運用上の都合」で同一証明書を複数取引先に配布したケース。1社の侵害で全接続が危険にさらされる。
取引先担当者の退職後も接続継続
取引先のシステム担当者が退職した後も、その担当者のIDで接続が継続されていた事例。

問題3: 退職後も残るパートナー接続

SIer・保守ベンダーの担当者がプロジェクトを離任した後も、VPN接続・踏み台サーバーへのアクセス権が残存するケースは非常に多いです。 特に長期保守契約では「念のため」という理由でアクセスを残す慣行があります。 これは内部不正・元委託先による不正アクセスの主要リスクとなります。

✅ 対策の基本方針: 外部ユーザーのIDにはすべて「スポンサー（社内の連絡責任者）」を設定し、 スポンサーが四半期ごとにレビューし続けている限りのみアクセスを維持する仕組みを構築します。 スポンサーが退職した場合は外部IDを自動停止する連動が理想的です。

🔌 EDI・API認証の近代化

固定パスワード接続・バイナリプロトコル から OAuth 2.0・APIゲートウェイへ

日本企業のEDI（電子データ交換）環境は、1990〜2000年代に構築されたJX手順・全銀TCP/IP手順・バイナリVPN接続が現役稼働しているケースが多く、 認証は固定パスワードや共有秘密鍵に依存しています。これらのシステムの近代化は、セキュリティ向上だけでなくコスト削減・開発生産性向上にもつながります。

mTLS（相互TLS）証明書管理

機密性の高いB2B接続（金融・医療・官公庁向け）では、OAuth 2.0にmTLS（RFC 8705）を組み合わせた「Certificate-Bound Access Token」が標準的な強化策です。 クライアント証明書とアクセストークンをバインドすることで、トークンが盗まれても他のクライアントからは使用不可になります。

🔐 証明書ライフサイクル管理

  • 有効期限: 1〜2年（自動更新推奨）
  • プライベートCAの構築（Azure Private CA等）
  • 証明書台帳のCMDB登録
  • 期限30日前アラートの設定
  • 失効（CRL/OCSP）確認の実装

🔑 証明書発行プロセス

  • 取引先のCSR（証明書署名要求）を受領
  • 担当者の本人確認（契約書との照合）
  • プライベートCAで署名・発行
  • セキュアチャネルで証明書を配布
  • 発行記録のタイムスタンプ保存

⚠️ よくある落とし穴

  • 証明書の有効期限切れによる業務停止
  • 複数取引先への同一証明書配布
  • 失効証明書の即時CRL反映遅延
  • 中間CA証明書の管理漏れ
  • 担当者異動時の証明書引き継ぎ

🔒 セキュリティ要件 — ゼロトラスト原則での外部アクセス

外部ユーザーはゼロトラストモデルにおいて最も検証が必要な存在です。 「信頼するネットワーク内にいるから安全」という前提が通用しない外部アクセスは、 すべてのリクエストを常に検証するゼロトラスト原則の適用が必要です。

📜 規制対応 — 個人情報保護法・金融庁GL対応での外部ID管理

📋 改正個人情報保護法（2022年全面施行）対応

  • 外部提供記録義務: 取引先への個人データ提供の記録（提供先・提供日・データ内容）
  • 外部委託先への監督義務: 委託先が適切な安全管理措置を講じているかの確認・監査
  • 越境データ移転規制: 外国の取引先への個人データ移転は同等措置の確認が必要
  • ID管理との連動: 外部ユーザーのアクセスログが「提供記録」の一部となる設計

🏦 金融庁 サイバーセキュリティGL対応

  • 第三者委託管理: 委託先のセキュリティ管理レベルの定期評価
  • アクセス権管理: 委託先へのアクセス権は業務上必要な最小限に
  • ログ保全: 委託先のアクセスログを7年間保全（金融機関の場合）
  • インシデント報告: 委託先経由のインシデントも1時間以内の報告義務

🔍 J-SOX（内部統制）での外部ID管理証跡

  • アクセス権の付与・変更・削除の承認記録
  • 四半期ごとの外部ユーザーレビュー（Certification）記録
  • SOD（職務分離）チェック結果の記録
  • ITGCの一環としてアクセスログの定期レビュー

🌐 その他規制・フレームワーク

  • ISMS（ISO/IEC 27001）A.9: アクセス制御管理への準拠
  • PCI DSS v4.0 要件8: IDおよびアクセス管理（外部ユーザー含む）
  • NIST SP800-63B: 外部ユーザーのIAL（本人確認レベル）定義
  • GDPR: EU取引先がある場合のデータ処理契約（DPA）

監査ログの設計要件

外部ユーザーのアクセスログは、内部ユーザーと同等以上の詳細度が必要です。 特に「誰が・いつ・どのシステムに・何をしたか」を証明できるログ設計が監査対応の基本となります。

アクセスログ アクセスリソース・操作種別（読取/書込/削除）・データ量・セッション時間 5年 SIEM / データレイク

💡 低コストで始める方法

Phase 1（棚卸し）はコストゼロで可能。 PowerShell/Graph APIを使ったEntraゲストアカウント棚卸しスクリプトを実行するだけで ゴーストIDを発見・削除でき、コスト削減と即時リスク低減が達成できます。

💼 M365既存環境の活用

Microsoft 365 E3/E5を導入済みの企業は Entra ID Governance（P2ライセンス）を追加するだけで高度なB2B管理が可能です。 追加投資は最小限でB2B Certificationを実現できます。

🏢 大規模EDI近代化のROI

EDIのAPI化は「電文仕様の変更コスト削減」「取引先オンボーディング期間短縮（6ヶ月→2週間）」 「インシデント対応コスト削減」を合わせると、3〜5年でROI達成が一般的です。

✅ まとめ: 外部ID管理は「まず棚卸し」から始めることが最も重要です。 既存のゴーストアカウントを発見・削除するだけで即時リスク削減とコスト削減が実現できます。 その上でPhase 2（B2B IdP統合）でゼロトラスト原則に基づく外部アクセス制御を整備し、 Phase 3（自動オンボーディング）で運用効率を最大化するロードマップを推奨します。 EDI近代化は長期的なセキュリティ基盤強化として並行して進めることが理想的です。
