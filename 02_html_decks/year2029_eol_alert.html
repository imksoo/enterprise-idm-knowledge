⚠ Section 2: EOL後の具体的リスク

セキュリティパッチなし / ESU費用増 / 監査指摘 / サポート撤退 — 4大リスクの詳細

🔴 ① セキュリティパッチなしで脆弱性が蓄積

CVE蓄積：月10〜30件

EOL後のWindows Serverには、Microsoftからセキュリティ更新プログラムが提供されなくなります。OSカーネル・Active Directoryサービス・Kerberos実装に発見された脆弱性は未修正のまま残存し、攻撃対象になります。

  • Kerberoasting / Pass-the-Hash 攻撃の成功率向上
  • ゼロデイ脆弱性が公開情報として攻撃に利用される
  • ランサムウェアグループはEOL製品を優先的に狙う
  • ESU未契約時はYear1翌日からパッチゼロ

🟡 ② ESU（延長セキュリティ更新）費用の逓増

3年累計：ライセンス費の3倍超

MicrosoftはEOL後もESUを最大3年間提供しますが、費用はライセンス費の75% / 100% / 125%が毎年加算されます。Azure上での利用は無償ですが、オンプレミスでは追加費用が不可避です。

  • Windows Server 2019: ESU Year1〜3（2029〜2032年）で逓増
  • Windows Server 2012 R2: ESU Year3まで（〜2026年10月）
  • ESU期間終了後は完全にパッチなしとなる
  • ESU費用は移行コストの一部に充当できない「消費的支出」

🟣 ③ 監査・コンプライアンス指摘

PCI DSS: 不適合 / ISMS: 指摘必至

PCI DSS v4.0、ISMS（ISO 27001）、J-SOX、金融機関向けFISC安全対策基準はいずれも「サポートされているソフトウェア・OSの使用」を要件として規定しています。EOL製品の継続使用は審査での不適合・指摘事項として記録されます。

  • PCI DSS 6.3.3: セキュリティパッチの適時適用が必須
  • ISMS A.8.8: 技術的脆弱性の管理（EOL製品は管理不能）
  • J-SOX: IT全般統制評価での指摘が財務報告リスクに波及
  • 監査法人・外部審査員によるASMR是正要求が増加

🟢 ④ ベンダー・SIerサポートの撤退

障害対応工数：最大10倍増

EOL製品に対しては、Microsoft社による技術サポート（問い合わせ対応）も終了します。SIer・保守ベンダーも EOL製品のサポート継続には追加費用が発生するか、サポート不可となるケースが増えています。

  • Microsoft サポートへの技術問い合わせ不可（EOL後）
  • SIer保守契約でEOL製品除外条項が適用されるケース増加
  • 障害発生時の原因調査・復旧に「経験頼り」しかなくなる
  • 新規周辺製品・SaaSとのインテグレーション保証なし
🚫 複合リスクの発動：EOL後に重大なセキュリティインシデントが発生した場合、「EOL製品を使用し続けていた」という事実が取締役の善管注意義務違反・株主代表訴訟・監督官庁からの業務改善命令の根拠として使われる可能性があります。

🔄 Section 3: EOL対応 3選択肢 比較表

ESU延命 / インフラ移行（オンプレ継続） / クラウド移行 — コスト・メリット・デメリット・期間
⚠ 3つの選択肢は排他的ではありません。実際には「一部システムをESU延命しながら段階的にクラウド移行する」組み合わせ戦略が現実的です。
比較軸 🔴 選択肢A: ESU延命 🟡 選択肢B: インフラ移行（オンプレ継続） 🟢 選択肢C: クラウド移行

初期コスト 低（ESU費のみ） 中（ハードウェア・ライセンス・工数） 中〜高（移行プロジェクト費用）
3年間の総コスト 高（ESU年75%→100%→125%） 中（移行後は通常運用コスト） 中〜低（ライセンス型で柔軟）
セキュリティリスク 高（EOL製品に依存、アーキテクチャ変わらず） 中（最新OSで軽減、設計次第） 低（ゼロトラスト・MFA・条件付きアクセス適用可）
対応期間 短（即時） 中（6〜18ヶ月） 長（12〜36ヶ月）
業務継続性 高（変更なし） 中（移行期の並行稼働が必要） 中（アプリ互換性テストが必要）
将来性 低（3年後に再度EOL問題） 中（次のEOLまでの時間稼ぎ） 高（クラウドネイティブへの布石）
オンプレ依存脱却 なし なし（オンプレ継続） あり（ハイブリッド→クラウドへ移行）
コンプライアンス改善 限定的（パッチは来るが古アーキテクチャ） 中（最新OSでパッチ適用可） 高（ゼロトラスト実装でISMS/PCI DSS適合強化）
Active Directory依存 継続 継続 段階的削減（Entra ID Hybrid Join経由）
推奨タイプ 移行計画策定中の短期ブリッジのみ クラウド移行が困難なオンプレ残存系システム 新規システム・SaaS中心企業・中長期戦略

🔴 選択肢A の注意点

  • ESUはあくまでセキュリティパッチのみ（機能追加なし）
  • 3年後に再度EOL対応が必要で根本解決にならない
  • ESU費用を移行準備資金として確保することを推奨
  • 最長でも1〜2年の延命にとどめるべき

🟡 選択肢B の注意点

  • Windows Server 2022/2025 へのアップグレード or 新規調達が必要
  • ハードウェアのEOL（サーバー保守期限）と合わせて判断
  • Active Directory のドメイン機能レベル引き上げに注意
  • DCのOS更改と役割移行（FSMO）の計画が必要

🟢 選択肢C の注意点

  • Entra Hybrid Join から段階移行が現実的
  • オンプレ専用アプリはAzure AD DS / ドメイン参加VMが必要
  • Kerberos認証が必要なアプリは移行難易度高
  • グループポリシー代替としてIntuneの設計が必要

🏭 Section 5: NSSOLサービスメニュー

現状調査から移行支援・運用サポートまで — IDM近代化を一貫支援
NSSOL（日本製鉄ソリューションズ）は、製造業・金融・流通・医療など幅広い業種でActive Directory / Entra ID / PAM / IGA の設計・移行・運用を支援しています。EOL対応の緊急性から逆算した現実的な計画策定を得意とします。
STEP 1

🔍 IDM現状調査・リスクアセスメント

  • Active Directory / LDAP 環境棚卸し
  • EOLカレンダー作成（製品別・サーバー別）
  • 特権アカウント・退職者アカウント棚卸し
  • MIM 2016 依存システムマッピング
  • セキュリティリスク評点（CVSS準拠）
  • 経営報告書（CIO向けサマリー）作成
💰 初回アセスメント：無償〜100万円（規模による）
STEP 2

📄 IDM近代化 移行計画策定

  • EOLデッドライン逆算ロードマップ作成
  • 3〜5年の投資計画・ROIシミュレーション
  • Entra ID / PAM / IGA 製品選定支援
  • 段階移行設計（Hybrid Join → クラウド）
  • RFP作成支援・ベンダー評価支援
  • 情報システム部門・経営層向け説明資料作成
💰 計画策定：300万〜800万円（規模・期間による）
STEP 3

🔄 移行支援（設計・構築・テスト）

  • Windows Server 2022/2025 DC更改・移行
  • Entra Hybrid Join / Entra Join 展開
  • MIM 2016 → IGA製品（Saviynt/SailPoint等）移行
  • PAM 導入（CyberArk / Delinea）
  • Microsoft Sentinel SIEM 構築・チューニング
  • Red Hat IdM / 389 DS 移行（Linux認証）
💰 移行支援：1,000万〜5億円（環境規模による）
STEP 4

🛠 運用サポート・継続的改善

  • Active Directory / Entra ID 運用代行
  • 月次セキュリティレポート・脆弱性監視
  • IDM設定変更・ライフサイクル管理支援
  • インシデント発生時の緊急対応（24/7対応オプション）
  • 次期EOLに向けた継続的ロードマップ更新
  • セキュリティ教育・管理者トレーニング
💰 運用サポート：月次100万〜500万円（SLAによる）

📎 FAQ・補足資料

よくある質問と参考情報

よくある質問

質問回答
ESUを契約すれば2029年以降も安全か？ セキュリティパッチは受け取れますが、アーキテクチャの根本的なリスク（横展開しやすいAD構造・MFA未適用等）は解消されません。ESUはあくまで移行準備中の「時間稼ぎ」です。
Entra ID移行でオンプレのアプリはどうなるか？ Kerberos / NTLM 認証が必要なアプリは、Entra ID の「Entra Domain Services（Azure AD DS）」または Hybrid Join で対応できます。完全クラウド移行の前に互換性調査が必要です。
Windows Server 2025 は長期使えるか？ Windows Server 2025 の延長サポートは2034年10月9日まで。オンプレ継続の場合の移行先として推奨されます。ただし、同時にクラウド移行計画も並行して立案することを推奨します。
Red Hat IdM と Active Directory は共存できるか？ はい。Red Hat IdM の「AD Trust」機能を使用することで、Linux 環境は Red Hat IdM で管理しつつ、Windows 環境の Active Directory と相互認証できます。ハイブリッド企業に推奨の構成です。
MIM 2016 の延長サポート終了後に何が起きるか？ 2026年7月14日以降、セキュリティパッチが提供されなくなります。プロビジョニング機能自体は動作しますが、脆弱性が発見されても修正されません。また、Microsoft のテクニカルサポートも受けられなくなります。
OpenLDAP から Red Hat IdM への移行は難しいか？ スキーマ・属性設計が大きく異なるため、単純なデータ移行ではなく「認証基盤の再設計」に近い作業です。特にアプリが OpenLDAP 固有の bind/search フォーマットに依存している場合、アプリ側の改修が必要になることがあります。
⚠ 本資料の情報について：EOL日程はMicrosoft・Red Hatの公式情報に基づきますが、変更される場合があります。最新情報は各ベンダーの公式サポートサイトでご確認ください。
