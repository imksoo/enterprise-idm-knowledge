🔗 SaaS SSO設定クイックスタート

社内SaaSを一つのIDで管理 ― 退職者のID停止を一括処理する仕組みを最速で作る

SSOで何が変わるか

❌ SSOなし：現在の苦痛

  • SaaSごとに別のID/パスワードが必要
  • 退職者が出たら全SaaSに個別連絡して停止依頼
  • 「Aさんのslackはどうなった？」と確認作業が発生
  • 停止もれで元社員がシステムにアクセス
  • 社員もパスワード管理に疲弊

✅ SSOあり：理想の状態

  • 1つのID（会社のGoogleまたはMicrosoft）で全SaaSにログイン
  • 退職者のGoogle/MicrosoftアカウントをOFFにすると全SaaSも使えなくなる
  • 新入社員のオンボーディングが当日完了
  • どのSaaSに誰がアクセスしているか一覧把握可能
  • パスワード管理の負担ゼロ

どのIdPをSSO基盤にするか（まず選択）

🟢 Google Workspace を使う場合

条件：Google Workspaceを既に使っている

コスト：Business Starter（約700円/月/人〜）でSSO可能

設定方法：各SaaSの管理画面で「SAMLでGoogleを使う」を選択するだけ

対応SaaS：Slack、GitHub、Zoom、Salesforce、Jira、Confluence等500種以上

🔵 Microsoft 365 を使う場合

条件：M365 Business Premium以上（またはEntra ID P1）

コスト：Business Premium 約3,300円/月/人（MFAも含む）

設定方法：AzureポータルからEnterprise Applicationsに各SaaSを追加

対応SaaS：上記に加えAzure/AWSなどクラウドサービスも充実

💡 どちらを選ぶべきか：すでに使っている方を選ぶのが正解です。まだどちらも使っていない場合は、将来的にWindowsサーバーやAzureを使うならM365、Google系ツールが多いならGoogle Workspaceを推奨します。

まず3つのSaaSから始める（推奨手順）

Slackにまず設定する（最も効果が高い）
Slack管理画面 → 設定 → 認証 → SAML認証を有効化 → IdP（Google/Microsoft）の設定URLを入力。完了後は退職者のGoogleアカウントを止めるとSlackも自動ロックされます。
GitHub Organizationに設定する（エンジニアチームに重要）
GitHubOrg設定 → Security → SAML SSO。個人GitHubアカウントのまま使えますが、OrgリポジトリへのアクセスにはSSO認証を通ることが強制されます。退職後はOrgメンバー除外で即アクセス不可。
AWSにSSOを設定する（最優先でセキュリティ効果大）
AWS IAM Identity Center（旧AWS SSO）を有効化 → IdPとSAML連携を設定。IAMユーザーの個人アカウントをIAM Identity Centerに移行するとシングルポイント管理が実現します。
この3つだけで、最もリスクが高い「Slackの元社員アクセス」「GitHubの元社員アクセス」「AWSの元社員アクセス」がワンアクションで止まるようになります。
