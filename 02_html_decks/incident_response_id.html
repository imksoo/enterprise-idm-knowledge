🚨 IDインシデント対応プレイブック

アカウント侵害・ランサムウェア・特権ID乗っ取り時の初動対応手順 | 2026-04-07 | NSSol IDM参照資料

⚠️ 本書の使い方： インシデント発生時は感情的にならず本書の手順に従ってください。 最初の30分の行動が被害を10分の1にする可能性があります。勝手な「復旧作業」は証拠を消し、被害を拡大させます。

シナリオ別対応手順

シナリオA: 管理者アカウントの乗っ取り疑い

T+0〜5分状況確認（ログを見る、動かさない）
  • Entra ID サインインログ / AD セキュリティイベントログで不審な認証元IPを確認
  • 問題のアカウントの最近の操作（GPO変更・ユーザー追加・ファイル削除）をログで確認
  • CISOと上長に即報（口頭+Slack/Teamsプライベートチャンネル）
T+5〜15分侵害アカウントの隔離（無効化）
  • Entra ID: 対象ユーザーをサインインブロック。全セッションを失効（Revoke sessions）
  • AD: 対象ユーザーをDisable。AD属性でsmartcardLogonRequired=Trueに設定（追加保護）
  • PAM: 対象ユーザーに紐づいた特権セッションを強制切断
  • MFAデバイスの登録情報もクリア（乗っ取り者が登録したMFA削除）
T+15〜60分横移動の痕跡調査
  • 侵害アカウントがアクセスした全リソースリスト（Entraサインインログ90日分）を取得
  • ADで新規作成ユーザー・GPO変更・グループメンバー追加を確認（過去24〜72時間）
  • SIEMでLateral Movement指標（Pass-the-Hash / Pass-the-Ticket）を検索
  • 影響を受けたサーバーはネットワーク隔離（VLANセグメント分離）検討
T+1〜24時間復旧計画と再発防止
  • 侵害の根本原因特定（フィッシング / 弱パスワード / 未パッチ脆弱性 / インサイダー）
  • 侵害アカウントのパスワードリセット + MFA再登録（本人確認後）
  • KRBTGT パスワード変更（Golden Ticketが作られた可能性がある場合、24時間間隔で2回）
  • 証拠保全：ログをSOC/SIEMに長期保存。法的対応の可能性があれば改ざん防止保存。

シナリオB: ランサムウェア感染・ID基盤への波及確認

T+0〜10分ADの安全性確認（最優先）
  • DCへのネットワーク疎通確認（pingとポート確認）
  • ADイベントログ4625（ログイン失敗）・4720（ユーザー作成）・4728（グループ追加）を確認
  • DCのC:/Windows/NTDS/ntds.dit のタイムスタンプ確認（改ざんされていないか）
  • AD DCをネットワーク的に最高優先度で保護（DCへのRDP・SMBを一時制限）
T+10〜30分特権IDの緊急保護
  • Domain Admins グループのメンバーを全員確認（不審なアカウントを即無効化）
  • Enterprise Admins / Schema Admins グループも同様に確認
  • PAMシステムでサービスアカウントのパスワードを全件緊急ローテーション
  • Entra ID の緊急アクセスアカウント（Break-glass）の安全性確認
T+30分〜4時間復旧優先順位の決定
  • AD自体の健全性確認（ADバックアップからの復旧が必要かを判断）
  • DCのスナップショット/バックアップの取得状況確認（過去いつのバックアップが使えるか）
  • KRBTGT パスワードが漏洩した可能性がある場合は、ADフォレスト全体の復旧（Forest Recovery）を検討
  • 感染端末とADの間のネットワーク経路を遮断しながら段階的復旧

KRBTGT パスワード変更手順（Golden Ticket対策）

⚠️ KRBTGTとは？なぜ変更が必要か

KRBTGTはKerberosチケット発行サービスアカウントです。このパスワードが漏洩すると、攻撃者は任意のユーザーに「なりすます」Kerberosチケット（Golden Ticket）を偽造できます。このGolden Ticketは最大10年間有効で、パスワードを変えても無効化されません（KRBTGTのパスワードを変えるまで）。

重要：KRBTGTパスワード変更は24時間間隔で2回実施が必須です。 1回目でGolden Ticketを無効化、2回目で前のKRBTGTパスワードのキャッシュを完全に削除します。
