AD近代化ロードマップ

オンプレミスから始まる3つの移行パターン — 情報システム部長・ITアーキテクト・SE向け

このドキュメントは、オンプレミスActive Directory環境を抱える日本企業が次世代ID基盤へ移行するための実践的ロードマップです。 「Lift & Shift（DC移行型）」「Hybrid Coexistence（ハイブリッド同居）」「Cloud Native（クラウドネイティブ）」の3パターンを詳解し、 自社に合うパターン選択基準・失敗回避策・24ヶ月の具体的な移行計画を提供します。

日本企業の課題あるある

📅 ドメインコントローラー老朽化

実態: 「2012年導入のDCがまだ本番稼働中」「ハードウェア更改時期は2026年末」「Server 2012/2016の延長サポート終了が迫っている」。老朽DC上で動くADは、セキュリティパッチが不十分で高リスク。

📊 グループポリシー肥大化

典型例: プロジェクトのたびに追加されたGPOが積み上がり、「削除したら何かが壊れる気がして誰も手をつけられない」状態。GPO棚卸しをすると、有効なものは全体の30%以下だったというケースが多い。

🧳 サービスアカウント管理不能

実態: 中規模企業でサービスアカウント200〜500個。「オーナー不明」「パスワード不明（変更したら壊れる）」「停止影響不明」の三重苦。SIer委託先が管理している場合、契約終了で引き継ぎ資料すら消滅。

👴‍♂️ ベンダー共有ID問題

典型例: 「SIer保守チームが全員同じAdministratorで作業」「誰が何をしたか証跡なし」「保守契約が5社あるが、全員同じIDを使っている」。J-SOX監査でも問題視されるケース。

📦 パターン1: Lift & Shift（DC移行型）

対象: DCクローズ急ぎ・AD構成変更不可・短期実現優先 — 所要期間: 6〜12ヶ月

🎯 このパターンが適する企業

  • オンプレミスDCのハードウェア更改期限が迫っている
  • AD構成を大きく変更したくない（影響範囲が大きすぎる）
  • まずDCをクラウド移行し、後工程で段階整理したい
  • 予算・リソースが限られ、短期での完了が必要

⚠️ このパターンの注意点

  • AD設計問題（GPO肥大化・OU混乱）をそのまま持ち込む
  • Azure VM上のADは運用コストが発生し続ける
  • 「移行完了」ではなく「延命」と割り切ることが重要
  • 将来のHybrid/Cloud Native移行計画を同時に策定すること

移行ステップ

1
Phase 1: 事前評価・設計（2〜4週間） ADフォレスト構成・信頼関係・DNS設計の確認。Azure Virtual Network設計・ExpressRoute/VPN接続帯域確認。Azure VM サイジング（DC x2 + 管理サーバー）。移行ツール選定（Azure Migrate / 手動DC昇格）。
2
Phase 2: Azure環境構築・DC昇格（4〜8週間） Azure Virtual Network + サブネット構築。Azure VM（Windows Server）へのAD DS役割インストール。既存ドメインへの追加DC昇格・レプリケーション確認。Azure側DNSの設定・クライアントへの配布。
3
Phase 3: 切り替え・旧DCの縮退（2〜4週間） PDCエミュレーター等FSMOロールのAzure DC移動。クライアントPCのDNS向き先変更・動作確認。旧オンプレDCの降格・縮退・ハードウェア撤去。Entra Domain Servicesの設定（LDAP/Kerberos補完が必要な場合）。
項目詳細
所要期間6〜12ヶ月（事前評価含む）
コスト感Azure VM（DC x2）+ ネットワーク費用 ≈ 月額30〜80万円。初期構築費50〜200万円（規模による）
主なリスクAzure ExpressRoute/VPN帯域不足による認証遅延。FSMO移動ミスによる認証停止。DNS設定誤りによる全社影響。
ADオンプレ継続不要（Azure VMへ移行）。ただしAD設計問題は引き継ぐ
推奨度DC更改目的には有効 セキュリティ改善には不十分

🔄 パターン2: Hybrid Coexistence（ハイブリッド同居）★ 日本企業主流

対象: 段階移行・既存資産活用・リスク分散 — 所要期間: 12〜24ヶ月
なぜこれが日本企業の主流か: ファイルサーバー・Kerberos依存アプリ・Windows Server管理・SIer委託運用が長く残る日本企業では、ADを即廃止できません。Hybrid CoexistenceはオンプレミスADを維持しながらEntra IDの機能を段階的に使い始められるため、リスクを抑えた現実的な選択です。

🎯 このパターンが適する企業

  • Microsoft 365をすでに使っているまたは移行予定
  • ファイルサーバー・Kerberos依存アプリが残存
  • 全社一斉変更は難しく、段階移行したい
  • 従業員1,000名以上の中〜大規模企業
  • SIer委託運用が前提で内製化が限定的

⚠️ 注意すべき落とし穴

  • Entra Connect設定ミスで全社同期障害リスクあり
  • UPN（メールアドレス）とADログイン名の不一致問題
  • ハイブリッドを「永続状態」にしないよう計画を明示する
  • MFA例外ポリシーの肥大化に注意

移行ステップ（推奨: Phase 1〜4）

1
Phase 1: ハイブリッド基盤構築（3〜6ヶ月） AD健全性確認（孤立OU・未使用アカウント・GPO棚卸し）。Entra Connect Sync導入（属性同期設計・フィルタリング設定）。Password Hash Synchronization（PHS）有効化。Entra Hybrid Join設定・パイロット端末での動作確認。UPN/メールアドレス統一（サフィックス変更が必要な場合は早期対処）。
2
Phase 2: 認証強化・MFA全社展開（3〜6ヶ月） Conditional Access（条件付きアクセス）ポリシー設計・段階展開。Microsoft Authenticator全社員登録（ヘルプデスク体制整備必須）。MFA例外アカウント・緊急除外アカウント定義。SaaSアプリのSAML/OIDC統合（Entra ID経由SSO化）。AD FSが存在する場合の廃止計画策定。
3
Phase 3: 特権管理強化（3〜6ヶ月） Windows LAPS（ローカル管理者パスワード個別管理）全端末展開。Domain Adminsの最小化・Tier 0分離設計。JIT（Just-in-Time）特権昇格の仕組み導入。ベンダー保守アカウントの個人ID化・証跡取得。Privileged Identity Management（PIM）設定。
4
Phase 4: ADフリー化の範囲拡大（6〜12ヶ月+） 新規PC調達時はEntra Joinに切り替え（GPO依存排除確認後）。IntuneによるGPO代替ポリシー設計・段階適用。レガシーアプリの認証方式調査・SAML/OIDCへの移行またはアプリ廃止。残存ファイルサーバーのSharePoint/OneDrive移行検討。

☁️ パターン3: Cloud Native（クラウドネイティブ）

対象: 新規事業・スタートアップ・全社クラウド化済み — 所要期間: 3〜9ヶ月
このパターンの前提: オンプレミスADが存在しない、またはゼロから新環境を構築できる場合に適します。レガシーシステムが多い既存の大企業が「今すぐCloud Nativeへ」は現実的ではありません。新規子会社・新規事業立ち上げ・スタートアップが対象です。

🎯 このパターンが適する組織

  • 新設会社・新規事業部門でADが存在しない
  • 全社員がSaaS・クラウドのみを使用
  • ファイルサーバー・Kerberos依存アプリがない
  • モバイル・リモートワーク中心の組織
  • スタートアップ・Tech企業

⚠️ レガシーアプリ対応課題

  • Kerberos認証を要求するアプリは別途対処が必要
  • SMB/CIFSファイル共有 → SharePoint/OneDrive移行
  • Windows Server管理認証 → Azure Bastion等で代替
  • LDAP Bind要求アプリ → Entra Domain Services補完

🧭 Section 5: 選択基準フロー（質問形式）

3つの質問でパターンを絞り込む
❓ Q1: オンプレミスのファイルサーバー（SMB/CIFS）を継続利用する必要がありますか？
✅ はい（継続利用する） AD継続が必要。クラウドネイティブのみでは対応不可。
→ パターン1 または パターン2 へ進む
❌ いいえ（クラウドへ移行する） SharePoint/OneDriveへ移行可能ならAD不要も選択肢。
→ パターン3（新規）または パターン2（既存AD整理）
❓ Q2: 既存の業務システムでKerberos認証（またはLDAP連携）を使っているものがありますか？
✅ はい（Kerberos/LDAP依存アプリがある） ADを残す必要あり。クラウドネイティブ化のゴールは遠い。Entra Domain Servicesでの補完も要検討。
→ パターン2（ハイブリッド） が最有力
❌ いいえ（Kerberos/LDAP依存なし） ADへの依存度が低い。クラウド移行の障壁が少ない。
→ パターン3 も検討可能
❓ Q3: ドメインコントローラーのハードウェア更改・データセンタークローズ期限は1年以内ですか？
✅ はい（1年以内に期限あり） 期限優先のため、まずLift & Shiftで延命。並行してHybrid移行計画を策定。
→ パターン1 → その後 パターン2
❌ いいえ（1年以上猶予あり） 段階移行の計画が立てられる。Hybrid Coexistenceで着実に進める。
→ パターン2（ハイブリッド） が最推奨
💡 まとめ: 多くの日本企業では、Q1・Q2に「はい」と答えます。その場合はパターン2（Hybrid Coexistence）が最も現実的な出発点です。 ただし、Q3で「1年以内の期限あり」の場合は、まずパターン1でDCを延命してから、パターン2に移行するという二段階アプローチを取ります。

⚠️ Section 6: よくある失敗パターンと回避策（日本企業特有）

実際のプロジェクトで繰り返される5つの失敗

🚨 失敗1: Entra Connect Sync設定ミスで全社ロックアウト

Entra Connect Syncの属性同期設定を誤り、ADのユーザー情報がEntra IDで上書き・削除されて全社員がMicrosoft 365にログインできなくなった。

💻 症状 全社員がM365・SaaSにログイン不可。業務完全停止。
🔍 原因 同期スコープ・フィルタリング設定の未確認。UPN不一致。本番適用前のテスト不足。
✅ 回避策 必ずステージングモードで動作確認。パイロットOUで限定テスト後に本番展開。緊急除外アカウントを事前設定。
📊 発生頻度 高 Entra Connect移行案件の約20〜30%で何らかの同期問題が発生

🚨 失敗2: GPO依存アプリのIntuneへの移行漏れ

Entra Join端末（ADドメイン非参加）に移行したが、一部業務アプリがGPOで配布された特定レジストリ設定・証明書に依存しており、アプリが起動しなくなった。

💻 症状 特定アプリの起動エラー・設定欠落。影響が散発的で原因特定に時間がかかる。
🔍 原因 GPO依存の全量調査が不十分。「まあ大丈夫だろう」で進めたIntuneへの移行。
✅ 回避策 GPO棚卸しツール（GPRESULT・Microsoft Security Compliance Toolkit）で依存関係を全量マッピング。Entra Join移行前に全GPOのIntune代替設定を確認・テスト。
📊 発生頻度 非常に高 GPO棚卸しが不十分な案件の大多数で発生

🚨 失敗3: UPN/メールアドレス不一致問題

ADのUPN（例: tanaka@company.local）とメールアドレス（tanaka@company.co.jp）が不一致のため、Entra Connect同期後にユーザーが重複作成され、ライセンスが二重付与された。

💻 症状 ユーザーが二重登録。ライセンス超過。メールが届かない。SSOが効かない。
🔍 原因 ADのUPNサフィックスが非ルーティングドメイン（.local/.internal）。計画段階での確認不足。
✅ 回避策 Phase 1開始前にADのUPNサフィックスを公開ドメインに変更。Entra Connect実行前にIdFix（Microsoft提供ツール）でAD属性の問題を全量チェック。
📊 発生頻度 中〜高 日本企業の約40%が.localドメインを使用

🚨 失敗4: MFA例外ポリシーの肥大化

MFA展開時に「この端末は古くて対応できない」「このシステムはMFAが使えない」という例外申請が続出し、例外アカウントが全体の30%を超えてしまった。

💻 症状 MFA未適用アカウントが多数存在。「MFA全社展開完了」と言いながら実態は未適用。
🔍 原因 例外申請フローに承認基準がなく、部署からの「困る」に対してすべて例外化。
✅ 回避策 例外承認は情報セキュリティ責任者が個別判断。例外の有効期限（90日）を設定し自動失効。例外率5%以下を目標としてKPIで管理。
📊 発生頻度 中 組織変革管理（OCM）が不十分なプロジェクトで発生

🚨 失敗5: サービスアカウントのMFA対象化による業務停止

Conditional Access「全ユーザーにMFA必須」ポリシーを適用した際、サービスアカウント（バッチ・連携処理）も対象になり、夜間バッチが全停止した。

💻 症状 夜間バッチ・システム連携処理が全て認証エラーで停止。翌朝に発覚。
🔍 原因 サービスアカウントとユーザーアカウントの区別なくCondional Accessを適用。事前テストが不十分。
✅ 回避策 サービスアカウントは事前に全量把握し、専用の除外グループを作成。サービスアカウントはクライアント証明書またはWorkload Identityに移行することが長期的な解決策。

📅 Phase 1（M1〜M6）

ハイブリッド基盤: Entra Connect・Hybrid Join・UPN整備。最優先の安定化フェーズ。

📅 Phase 2〜3（M5〜M14）

認証強化・特権整備: MFA全社展開・Conditional Access・LAPS・ベンダーID整理。セキュリティの核心。

📅 Phase 4（M14〜M24+）

ADフリー化: Entra Join移行・Intune GPO代替・レガシーアプリ移行。24ヶ月で完了せず継続する場合も多い。

スケジュールの現実: 上記は中規模企業の標準スケジュールです。大規模企業（5,000名以上）や基幹システムのKerberos依存が多い場合は、Phase 3〜4だけで追加12〜24ヶ月を要することがあります。「24ヶ月で全完了」ではなく「24ヶ月でハイブリッド基盤を安定化し、セキュリティを大幅改善する」を目標に設定することを推奨します。
